## D-002 실행 권한과 격리

- 상태: 확정
- 날짜: 2026-07-15

### 결정

- Lab은 폐기 가능한 격리 환경 내부에서 풀액세스로 실행한다.

- Production은 읽기와 검증 중심으로 운영하고 외부 상태 변경은 승인받는다.

- 저장소 루트, 대량 파일, 백업 없는 데이터의 삭제는 자동 실행하지 않는다.

### 이유

### 결과

- Lab에는 호스트 파일, 자격증명, 사설 네트워크를 노출하지 않는다.
- push, PR, 배포, 메시지, 결제는 승인 대상이다.
- 시스템 샌드박스는 자율 실행 범위를 제한하고, 삭제 확인은 Agent OS 행동 정책으로 보완한다.
- 기본 Project 설정은 `workspace-write`, `approval_policy = "never"`, Developer OS 볼트 쓰기와 네트워크 허용으로 구성한다.
- Project는 Git, Lab은 폐기와 재생성을 기본 복구 수단으로 사용한다.

## D-005 비용 계측과 작업 흐름

- 상태: 파일럿
- 날짜: 2026-07-15

### 결정

- Stop Hook이 세션 누적 토큰과 마지막 모델 요청 토큰을 로컬 이벤트 큐에 자동 기록한다.
- 작업 간 사용량은 같은 세션의 연속 Stop 누적치 차이로 계산한다.
- ChatGPT 크레딧, API 과금, 관측 토큰은 서로 다른 지표로 저장하며 임의 환산하지 않는다.

- 영구 삭제, 되돌릴 수 없는 외부 행동, 검증된 복구 경로가 없는 변경만 실행 전에 확인한다.

### 한계

- `last_request`는 전체 턴이 아니라 마지막 모델 요청 한 건이다.
- 로컬 세션 토큰만으로 ChatGPT 크레딧이나 API 비용을 계산할 수 없다.
- 첫 Stop 이전에는 작업별 차이를 계산할 기준점이 없다.

### 오프디바이스 경로

## D-007 책임 기반 Tutor와 학습 깊이

- 상태: 파일럿
- 날짜: 2026-07-18
- 적용: 사용자가 기존 완료 후 일괄 설명보다 나을 것으로 판단해 활성 Tutor 스킬 적용을 승인했다.

### 결정

- Tutor의 학습 범위는 CEO, CTO, 개발자 같은 직함이 아니라 사용자가 소유한 결정, 검증할 결과, 감당할 실패로 정한다.
- 이해 깊이는 `L0` 용어와 지도, `L1` 작동 원리, `L2` 선택지와 트레이드오프, `L3` 검증/실패/복구, `L4` 직접 구현/디버깅으로 구분한다.
- 필수 이해는 사용자 책임, 실패 영향, 비가역성이 클수록 깊게 한다.
- 에이전트에 실행을 위임한 작업은 모든 구현 세부보다 의사결정과 검증에 필요한 충분한 깊이를 우선한다. 다른 적격 검토자 없이 사용자가 승인해야 하면 더 깊게 설명한다.
- 학습은 현재 결정에 필요한 `필수`, 반복, 전이 가치가 있는 `전략적`, 시간이 있을 때 탐구할 `호기심`으로 구분한다.
- 가역적인 실행은 수업 때문에 중단하지 않는다. 중요한 결정 지점이나 작업 완료 후 필요한 깊이만 설명하고, 전략적, 호기심 주제는 후속 후보로 남긴다.
- 사용자가 명시적으로 공부를 요청하면 현재 위험 수준을 넘어 더 깊게 학습할 수 있다.

### 검증

- 서로 다른 실제 작업 5건에서 목표 깊이, 설명으로 인한 실행 중단, 결정, 검증, 복구의 재설명 가능성, 후속 학습 후보의 재사용을 기록한다.
- 저위험 일회성 작업은 과잉 설명 없이 완료되고, 고위험 또는 핵심 결정은 최소 `L3`까지 다뤄지는지 확인한다.
- 파일럿 뒤 별도 학습 큐나 자동화가 필요한지 결정하며, 그전에는 Run의 후속 학습 후보를 사용한다.

### 롤백

- 정책이 과도한 설명이나 기록 부담을 만들면 Tutor를 기존의 완료 후 핵심 결정, 복구 설명 방식으로 되돌린다.
- 기존 Run은 변경하지 않으며 새 형식은 선택적 본문 구역이므로 제거해도 기록 원본은 손상되지 않는다.

## D-008 공급자 중립 지시사항 계층

- 상태: 확정
- 날짜: 2026-07-21

### 결정

- 지시사항의 단일 원본은 공급자 중립 코어(`agents/AGENTS.md`)에 둔다.
- Codex와 Gemini는 각자의 컨텍스트 파일을 코어에 심링크한다. 어댑터 파일을 두지 않는다.
- Claude는 `CLAUDE.md`에서 `@` import로 코어를 읽고, 그 아래 얇은 Claude 전용 구역만 유지한다. Claude Code는 AGENTS.md를 네이티브로 읽지 않고, 심링크는 어댑터를 놓을 자리를 없애기 때문이다.
- 항상 참인 지시만 코어에 둔다. 조건부로 참인 지시(특정 워크플로, 포맷)는 전부 스킬로 내보낸다.
- 코어의 상한은 50줄이다. 초과하면 스킬로 분리한다. 코어는 세 CLI가 매 세션 무조건 지불하는 컨텍스트 비용이기 때문이다.

### 이유

지시사항이 공급자별로 갈라지면 같은 작업의 에이전트 행동이 CLI에 따라 달라져 라우팅 실험의 비교 기준이 무너진다. 변환, 생성 파이프라인 대신 심링크와 import를 쓰는 것은 어댑터를 얇게 유지하기 위해서다.

### 검증

## D-010 에스컬레이션 이벤트 로깅

- 상태: 파일럿
- 날짜: 2026-07-21

### 결정

- 하위 티어에서 시작했다가 실패해 상위 티어로 재시도한 작업(에스컬레이션)과, 상위 티어에서 한 번에 끝난 기계적 작업(하향 후보)을 기록한다.
- 기록은 기존 `agent-os-friction --origin agent` 채널에 `escalation: <from>→<to> | <작업> | <이유>` 형식으로 남기고, 주간 리뷰가 집계해 routing.json 변경을 제안한다.
- 사후 토큰 회계는 라우팅 개선의 간접 신호이므로 정밀 측정 체계를 만들지 않는다. 에스컬레이션이 라우팅 오류의 유일한 직접 증거다.

### 이유

새 수집 인프라 없이 기존 마찰 기록 채널에 규약만 얹어, 라우팅 변경 제안이 감이 아니라 근거에서 나오게 한다.

## D-011 용어 체계 (유비쿼터스 랭귀지)

- 상태: 확정
- 날짜: 2026-07-22

### 결정

- 하나의 개념은 모든 계층에서 하나의 이름을 쓴다. 개념명과 구현명을 이중으로 두지 않는다.
- 라우팅 슬롯 이름은 행위자 명사로 통일한다: `planner` / `worker` / `reviewer` / `clerk`. 속성 형용사였던 `mechanical`은 `clerk`(판단이 필요 없는 정형 작업의 수행자)로 교체한다.
- 이름에는 정체성(역할)만 담고, 속성은 설정 필드에 둔다. `fast_worker`의 fast는 `effort = low`가, `critical_reviewer`의 critical은 reviewer의 본질이 이미 담고 있으므로 Codex 에이전트를 `worker`, `reviewer`로 개명한다.
- '티어'는 공식 용어에서 제외한다. 라우팅 슬롯은 **역할**, 작업 크기는 **작업 등급(T0/T1/T2)**으로 부른다. 두 개념이 '티어' 한 단어를 공유하며 충돌했기 때문이다.
- 에스컬레이션은 모델 교체가 아니라 **작업의 역할 재분류**로 정의한다. Sonnet에서 실패해 Opus로 다시 했다면, 바뀐 것은 모델이 아니라 그 작업이 worker급이라는 애초의 분류다.

### 검토 후 유지

- `T0/T1/T2`, `Run`/`Event`/`Ledger`: 개념 구분이 명확하고 대체 이득이 없다.
- Agent OS(시스템 정의)와 Developer OS(지식 볼트): 서로 다른 시스템에 서로 다른 이름이므로 올바른 구조다.
- 계정 래퍼 명령명(`gcodex`/`ncodex`/`magy`/`sagy`): 명명 축이 비대칭(계정 식별자 vs 우선순위)이지만, 근육 기억과 인증 상태 디렉터리 변경 위험이 통일 이득보다 크다. 규칙만 문서화한다: 접두사 한 글자 = 계정 구분자.

### 보류

- `developer-agent-os` 스킬명: Agent OS와 Developer OS 두 시스템 이름에 걸쳐 있어 혼동 후보다. 아카이브 체인 스킬 통합 시점에 재검토한다. (2026-07-28: 트리거였던 아카이브 체인은 D-018로 삭제, 계측 트랙 투영 착수 시 재검토로 대체)

## D-012 스크립트 생태 계약 (paths.env + 레지스트리)

- 상태: 실험 (판정일 2026-09-02)
- 날짜: 2026-07-22

### 결정

- `bin/` 스크립트의 공유 경로는 `agent-os/paths.env`를 단일 진실 공급원으로 한다. 우선순위: 환경변수 > paths.env > 스크립트 내장 기본값. 내장 기본값으로 떨어지면 `ops-event`에 `reason=paths-contract-fallback`을 남겨 다이제스트에서 계약 파손이 드러나게 한다.
- `agent-os/scripts.md`에 스크립트 컨벤션(언어 선택, 계층 구분, 관찰 배관)과 전 스크립트 레지스트리를 둔다. `dotfiles-doctor`가 ① paths.env 파싱 가능 여부 ② 레지스트리 vs `bin/` 실물 diff ③ 계약 미채택 하드코딩 파일 수를 감시한다.
- 소급 이관은 하지 않는다. 파일럿 표본 3개(`agent-os-vault-snapshot`·`agent-os-review-due`·`agent-os-friction`)만 이관하고, 나머지는 해당 파일을 어차피 손댈 때만 이관한다.
- 공유 라이브러리(언어별 헬퍼)는 이 실험이 통과하기 전에는 만들지 않는다.

### 기준선과 지표 (2026-07-22)

- 계약 미채택 하드코딩 파일: 9개 중 파일럿 3개 이관 → 잔여 6개. 목표: 단조 감소, 경로 변경 시 수정 지점 8곳 → 1곳.
- 성공: doctor 초록 유지, 기간 내 `paths-contract-fallback` 이벤트, 계약 관련 friction 합계 ≤ 1건.
- 킬 기준: 계약 기인 훅/스크립트 회귀 1건 → 즉시 롤백 검토. 레지스트리 diff 1주 이상 방치 → 레지스트리는 연극이므로 폐기. friction ≥ 2건 → 계약이 비용이라는 신호.
- 판정: 2026-09-02에 채택/폐기/수정. 폐기 시 paths.env 삭제. 각 스크립트는 내장 기본값으로 자동 복귀하므로 롤백은 파일 삭제로 끝난다.

### 이유

프레임워크가 아니라 계약+순환으로 시작한다. 측정은 기존 배관(doctor, ops-event, friction, 다이제스트)에 얹어, 실험 장치 자체가 새 유지비가 되지 않게 한다.

## D-014 dotfiles 에이전트 자산 재편 (기능 축 + 공급자 어댑터, 스킬 벤더링)

- 상태: 확정
- 날짜: 2026-07-25

### 결정

- 의미 규칙: `agents/` = **설비 세팅값**(고치면 에이전트가 다르게 일한다), `agent-os/` = **운전 일지, 계측 규격서**(고쳐도 에이전트는 그대로다). 공통/개별은 agents 내부의 2차 구분이다. 루트·`skills/`는 공급자 중립, `agents/<공급자>/`는 어댑터이며 어댑터 내부는 그 공급자의 홈 구조를 미러링한다.
- 불변식: **agent-os/에서 홈으로 나가는 심링크 0.** (이관: hooks.json → agents/codex/) `dotfiles-doctor`가 install.sh의 링크 소스에 agent-os가 등장하는지 감시한다.
- 2단 규약: 행동 변경은 DECISIONS.md 기록(결정)과 `agents/` 반영(승격)으로 완성된다. 반영 없는 결정은 미집행이다.
- 이동: `agy/`→`agents/gemini/`, `ai-tools/models.json`→`agents/models.json`(routing.json과 한 시스템인 라우팅 패키지), `conventions/`→`agents/conventions/`, `claude/`→`agents/claude/`, `.codex/`→`agents/codex/`, `scripts/` 해체(cleanclip→bin 승격, 나머지 은퇴→yggdrasil stash).
- 스킬 벤더링: upstream 스킬은 자작과 함께 `agents/skills/`에 평면 동거하고, 출처는 스킬별 `VENDOR.md`에만 기록한다(폴더 분리, frontmatter 기입 금지. 출신이 바뀌어도 이동이 없고 upstream diff가 깨끗하다). 매트 포컷 active 전량(28종)을 벤더링했고 플러그인 구독은 해지한다. 갱신은 VENDOR.md 기준 수동 diff. 대장은 `agent-os/upstreams.md`.
- 재검토 조건: 지도(README Layout, CONTEXT.md) 정비 후에도 agents/agent-os 이름 혼란이 재발하면 단일 우산(C안)을 재검토한다.

### 이유

혼란의 원인은 축 혼재(기능 vs 공급자), 훅 3곳 분산, 죽은 파일, 지도 부재였다. 공급자는 부패 자원(D-009)이라 공급자 축은 자산을 중립화할 때마다 파일 이동을 강제한다. 기능 축 + 얇은 어댑터만이 공급자 교체(S1), 새 자산 유형(S2), 중립화(S3)를 구조 변경 없이 흡수한다. 단일 우산(C안)은 불변식과 양립 불가(agent-os 안에서 링크가 나감)이고 경로 깊이 +1이 영구 비용이다. 벤더링은 "코드는 포크하되 지식은 구독한다"의 스킬판이다. 수정 권리를 얻는 대신 갱신을 수동 diff로 통제한다.

## D-015 결정 기록의 단일 정본 (개인 인프라 결정 포함)

- 상태: 확정
- 날짜: 2026-07-25

### 결정

- 확정 결정은 이 문서에만 쓴다. 핸드오프, Run, 리뷰 노트는 D-번호를 **인용만** 하고 결정을 새로 만들지 않는다.
- 범위에 개인 인프라, 도구 배치 결정을 포함한다(창고 호스트, 상시 실행 여부, 볼트, 라이브러리 경로 등). Agent OS 운영에 종속된 인프라는 Agent OS 결정이다.
- 결정이 바뀌면 새 문서를 만들지 않고 해당 D-번호에 `개정 <날짜> — <무엇을 왜>` 줄을 추가한다(선례: D-001의 개정, 재개정). 미확정은 `상태: 파일럿|후보`로 표시한다.
- **정본에 D-번호가 없으면 미결로 취급한다.** 과거 노트의 문장을 확정 결정으로 인용하지 않는다. 그 자리에서 판단하고, 남을 값이면 D-번호를 신설한다. "이미 결정됐다"로 판단을 닫는 것은 정본에 근거가 있을 때만 유효하다.
- 기존 mimir 노트는 삭제하지 않는다. 근거로 보존하고 확정된 것만 승격한다. 우선순위 줄(이 문서 서두)이 미승격 초안을 자동으로 누른다.
- 재검토 조건: 인프라 항목이 늘어 에이전트 행동 결정을 찾기 어려워지면 섹션 분할(행동/인프라)을 검토한다.

### 이유

우선순위 줄("역사적 기획서, 체크리스트와 충돌하면 이 문서를 우선한다")과 개정 메커니즘은 D-001부터 이미 있었다. 실패한 것은 범위다. 개인 인프라 결정이 D-번호를 받을 자리가 없어 에이전트가 세션마다 mimir 핸드오프에 상태, 개정 라인 없이 적었고, 서로를 폐기하지 못하는 초안이 쌓였다. 확정인지 초안인지, 최신인지를 판별할 수 없는 기록은 결정이 아니라 소음이다.

실제 사고(2026-07-25): 아이맥 Postgres 배치에서 에이전트가 미승격 초안(결재함 노트)을 확정 결정으로 인용해 더 최신인 판단을 기각했다. 두 기록은 애초에 양립했다. 결재함이 기각한 것은 FileVault 무인 부팅이고 계측 문서가 권한 것은 테일스케일 상시 접속 패턴이어서 같은 사안이 아니었다. 정본 조회로 시작했다면 "해당 D-번호 없음 → 미결 → 지금 판단"으로 끝났을 문제다.

새 대장을 만들지 않는 이유는 정본이 둘이 되면 같은 실패가 재발하기 때문이다. 범위만 넓히고 인용 규칙을 명문화하는 것이 가장 작은 수정이다.

## D-016 유휴 자원 회수 (소유권 있는 것만, 작업 중엔 개입 없이)

- 상태: 확정
- 날짜: 2026-07-26

### 결정

- 에이전트 도구가 남긴 유휴 자원(알림 프로세스, iOS 시뮬레이터)은 사람이 기억해서 정리하지 않는다. 상시 launchd 잡이 회수한다.
- **회수는 소유권이 확인된 것으로만 한정한다.** `agent-notify`는 자기가 띄운 `alerter`의 PID와 실행 경로를 이벤트에 기록하고 그것만 종료한다. 이름이 같다는 이유로 남의 프로세스를 죽이지 않는다. PID는 재사용되므로 신호 직전 실행 경로를 재확인한다.
- **작업 중에는 개입하지 않는다.** `simulator-reaper`는 Xcode, Simulator.app·`xcodebuild`·`xctest` 중 하나라도 살아 있으면 아무것도 하지 않고, 도구가 모두 꺼진 뒤 유예(기본 900초)를 넘긴 기기만 종료한다.
- **스스로 끝나지 않는 외부 도구에는 상한을 건다.** `persistent` 알림도 `persistent_seconds`(기본 1800) 안에서 종료된다. 상한은 취향이 아니라 alerter가 macOS 26에서 스스로 종료하지 않기 때문이다. 상한을 지키는 주체는 도구가 아니라 우리 쪽 프로세스 타임아웃이다.
- **해소 경로가 사람의 클릭뿐인 큐에는 만료를 둔다.** pending 알림은 `pending_ttl_days`(기본 3) 후 자동 확정한다. 로컬, Slack 양쪽이 모두 꺼진 이벤트는 도달할 곳이 없으므로 제시 즉시 확정한다. "알리지 마"를 "확인 대기"로 기록하면 해소가 원리적으로 불가능하다.
- **쌓인 양은 사람이 보는 자리에 노출한다.** statusline이 pending 10건 이상일 때 표시한다. 상시 노출은 배경 소음이 되어 정작 폭증했을 때 안 보이므로 임계를 둔다.
- 재검토 조건: 회수 잡이 작업 중인 자원을 건드리는 사고가 나면 유예 시간과 가드 조건을 재검토한다. `alerter` 상류가 종료 버그를 고치면 상한 값을 재검토한다.

### 이유

2026-07-26 사고. `alerter` 한 프로세스가 30.8GB, 여덟 개 합계 83GB를 점유해 24GB 머신에서 jetsam이 4분간 4번 터졌다. 별개로 시뮬레이터 2대가 Xcode 종료 후에도 19시간 동안 프로세스 463개, 29GB를 붙들고 있었다.

두 실패는 형태가 같다. **생성자가 사라져도 살아남는 자원에 아무도 소유권과 상한을 갖지 않았다.** `agent-notify`는 alerter를 띄우고 무한 대기했고(워커가 죽으면 alerter는 감시자를 잃는다), Xcode는 시뮬레이터를 띄우고 종료했다. 둘 다 "닫으면 정리된다"는 가정이 깨진 자리였고, 사용자가 앱을 모두 종료해도 메모리가 풀리지 않은 이유다.

노출의 부재가 이를 키웠다. 미확인 알림 902건이 쌓여 있었는데 그 숫자가 보이는 곳이 statusline에도, sweep 로그(0바이트)에도, 세션 훅에도 없었다. 902건 중 842건은 `AGENT_NOTIFY_POLICY=quiet`로 **의도적으로 침묵시킨** 이벤트였다. 사용자가 "알리지 마"라고 지정한 것을 시스템이 "확인 대기"로 기록했고, 화면에 뜬 적이 없으니 클릭할 대상도 없어 영구 적재됐다.

회수를 소유권으로 좁힌 것은 검수 지적을 받아서다. 초안은 이름이 `alerter`인 프로세스를 상한 초과 시 무조건 종료했고, 실측 프로브에서 다른 경로의 동명 프로세스가 대상으로 선택됐다. 이 머신엔 alerter 설치본이 하나뿐이라 오탐 경로는 없었지만, 모듈이 자기가 만들지 않은 프로세스를 죽이는 것은 조건이 아니라 설계가 틀린 것이다. 소유권을 기록하자 `ack --all`이 알림 제거를 건너뛰던 문제도 함께 풀렸다. 느린 `alerter --remove` 대신 소유 PID를 직접 종료하면 되기 때문이다.

## D-017 agent-notify 메뉴 막대 관제점 (pending과 배너 수명 분리)

- 상태: 파일럿
- 날짜: 2026-07-27

### 결정

- `agent-notify`의 pending 상태는 메뉴 막대 앱에서 상시 가시화한다. macOS 배너는 주의를 끄는 전달 수단이지 pending 상태의 정본 UI가 아니다.
- local `temporary`는 배너만 짧게 표시하며 이벤트를 자동 확인하지 않는다. 배너가 사라져도 메뉴 막대 배지와 목록에는 개별 ACK 전까지 남는다.
- 승인 대기(`PermissionRequest`)와 오류를 완료보다 우선 표시한다. 개별 ACK와 pane 이동을 기본 처리 경로로 제공한다.
- 일괄 처리의 기본 동작은 승인 대기를 보존하는 **완료 모두 확인**이다. 승인 대기를 포함하는 **전체 확인**은 경고 후 실행한다.
- 메뉴 막대 앱은 기존 CLI의 JSON 조회, mode, ACK, open 명령만 호출하는 얇은 UI로 둔다. 이벤트 저장소와 처리 규칙의 정본은 `agent-notify` CLI에 남긴다.
- 파일럿 동안 기본 mode는 `temporary local + delayed Slack`을 유지한다. 메뉴 막대 가시성이 실제로 승인 대기 누락을 막는지 확인한 뒤 `persistent`의 존치 범위를 재검토한다.
- 재검토 조건: 승인 요청을 메뉴 막대에서도 놓치는 경우, 앱 polling이 과도한 CPU, 메모리를 쓰는 경우, 또는 CLI와 UI 상태가 불일치하는 경우.

### 이유

사용자에게 가장 큰 불편은 작업 완료를 놓치는 것이 아니라 승인 질문을 인지하지 못해 작업이 무기한 멈추는 것이었다. `persistent` 배너를 늘리면 가시성은 좋아지지만 D-016의 `alerter` 장수, 메모리 사고 위험이 다시 커진다. 배너 수명과 pending 상태를 분리하면 대부분의 알림을 `temporary`로 유지하면서도 승인 대기를 메뉴 막대의 단일 프로세스와 상태 목록으로 계속 노출할 수 있다.

"세션을 나중에 찾기"는 asx가, "결정, 문서로 증류"는 handoff + domain-modeling + D-015 정본 규약이 맡고 있다. `summarize-youtube-playlist`는 휴면이 아니라 중복이다. 계정 라우팅, 쿼터 중단이 CLI에 내장되면서 스킬에는 절차만 남았고, 같은 CLI를 감싸는 vsummary에 절차를 합치면 한 스킬로 충분하다. 반면 handoff-session은 10개 repo에 산출물이 실존하고 가장 최근 갱신이 어제(07-27)인 현역이다.

## D-019 세션 읽기, 내보내기의 공통 계층 (asx 정본, 소비자는 그 위에)

## D-020 보안점검, 다이제스트 신호 복원 (오탐 채널 수술과 소비 경로 연결)

- 상태: 파일럿
- 날짜: 2026-08-04

### 결정

- `personal-ops security`의 리스너 식별자는 `프로세스명:포트`가 아니라 **프로세스명**이다. Apple 상주 데몬(rapportd, ControlCenter, sharingd)은 관찰 대상에서 제외한다. 기준선은 자동 갱신하지 않고 `personal-ops security --accept [ID …]`로만 승인한다. 알림은 변화 시 1회, 미승인 발견은 활성 목록에 정직하게 남는다.
- 즉시 Slack은 **high 전용**이다. medium 이하 변화는 리포트와 ops-digest 경유로만 가고, 해소-만 있는 변화는 알리지 않는다. 늘 무해한 알림은 채널 자체를 죽인다.
- `softwareupdate` 검사는 주 1회로 내리고, 사이 실행은 직전 결과를 이월한다(이월 없인 검사일마다 new/resolved 출렁임).
- 신규 상시 체크 3종: launchd 퍼시스턴스 diff(사용자/시스템 plist 집합), 자격증명 권한 스윕(ssh 키, gh, claude, aws, netrc, codex), 백업 경로 부재(tmutil).
- ops-digest 산출물은 mimir `40 Reviews/백그라운드 잡 다이제스트.md`에 쓰고, 신호(오류, 주의 발견, 침묵)가 있을 때만 agent-notify 1줄을 보낸다. message류 키가 없는 이벤트는 payload를 k=v로 폴백 렌더하고, 동일 (source, severity, message)는 ×N으로 접는다.
- 발신 규약: 백그라운드 잡의 실패는 `kind=error|finding` + 사람이 읽을 `message`를 포함한다. run/low로 위장한 실패(세션 수확 2세대)가 관측을 장님으로 만들었다. 부분 실패(codex-account-usage 프로파일 일부 고장)는 finding으로 낸다.
- 테스트는 실제 이벤트 스트림에 쓰지 않는다. emit mock 또는 `OPS_STATE_DIR` 격리. (과거 오류 버스트 일부는 테스트 실행 오염이었다.)
- gitleaks 공개 레포 시크릿 스캔은 이 수술에 넣지 않고 포트폴리오 레포 추출 절차의 공개 전 게이트로 미룬다.
- 재검토 조건: 프로세스명 단위 식별이 실제 이상을 놓친 사례가 나오면 실행경로, 코드서명 기반 식별을 검토한다. digest 알림이 무행동 소음이 되면(주 3회 이상 열람 없이 넘김) 발신 조건을 조인다.

### 이유

2026-08-04 감사. 22개 리포트 전수에서 정적 검사(SIP, Gatekeeper, FileVault, 인증 권한) 발화 0회, 활성 이상 11건 전원 오탐이었다. 역대 고유 발견 37건 중 20건이 재부팅마다 포트를 바꾸는 rapportd였고, 원인은 최초 1회 후 갱신 수단이 없는 기준선과 포트 단위 식별이다. digest는 발신부가 넣지 않는 키(message)를 렌더가 찾아 오류, 발견 섹션이 구조적 공백이었고, 산출물은 vault 밖에서 14일간 소비 0였다. 수술 직후 첫 실행이 방치된 `python -m http.server`(전 인터페이스 바인드, 25시간 경과)와 백업 경로 부재를 즉시 잡았다. 오탐을 걷어내면 같은 검사가 실제 신호를 낸다.

## D-021 백그라운드 자원 회수, 계측 위생 (무한 성장 스토어와 유령 지표 정리)

- 상태: 확정
- 날짜: 2026-08-04
- 개정: 2026-08-04. P2 위생 집행. battery(제3자 plist)의 stdout을 `/dev/null`로 돌려 분당 3줄 적재를 차단(진단용 stderr→battery.log는 유지, battery CLI가 maintain 재설정 시 plist를 다시 써 되돌아갈 수 있음), 잔여 로그 18MB 정리. dref는 chrome-* 잔해 240MB 삭제, WAL 4.4MB 즉시 체크포인트했고, 재발 방지(재색인 로그 변화, 지연 시에만, 재색인 직후 체크포인트, 수확 오류 severity medium+message)는 dref repo 커밋으로 처리. 서버 재시작은 개편 WIP를 활성화할 위험이 있어 다음 자연 재시작부터 적용된다.

### 결정

- 0→1도 같은 루프의 1단계부터다(라이트 루프를 따로 만들지 않는다). 제품이 없으면 1~3단계의 행동 증거와 15단계 기준값은 **현행 방식**(그 과업을 지금 하는 방법)의 관찰이다. 가설로 게이트를 통과하지 않는다.
- 1→99도 같은 루프, 진입점만 다르다: "이미 진행된 제품에 붙이기"(역매핑) 후 작은 바퀴 반복. 병행 비루프 차선: `diagnosing-bugs`(버그), `triage`(이슈 유입), `improve-codebase-architecture`(구조), `wayfinder`(다세션 결정).
- 매트 체인의 약점(호출 시점을 사람이 기억해야 함)은 **제안 트리거**로 메운다: 루프 안은 스킬 연결표가, 루프 밖은 developer-agent-os가 트리거 시점(새 핵심 도메인 개념→domain-modeling, 요구 모호→grill 제안, 기능 완료→code-review, 구조 우려→codebase-design)에 제안한다. 4 체크포인트(`grill-with-docs`·`to-spec`·`to-tickets`·`implement`)의 수동 호출은 유지한다. 외부 게시, 방향 확정 게이트다.
- superpowers(obra, 현재 v6.2.0, 스킬 14종)는 **전역 비설치**를 유지한다. 9+/14가 매트와 중복이고, SessionStart 훅이 매 세션 자체 라우터(using-superpowers)를 주입한다. 협업 등 필요한 컨텍스트에서만 지정 repo에 project 스코프로 설치하고, 그 repo `CLAUDE.md`에 "superpowers 정본, 매트 체인 미사용"을 명시한다. 지정 repo 밖은 매트 체인 우선.
- 비중복 후보 2종만 기록한다: `verification-before-completion`(완료 주장 전 신선한 증거. 채택 시 형태는 스킬이 아니라 AGENTS.md 코어 1줄 또는 훅, 항상 참 규율은 코어 소관 D-008)과 `subagent-driven-development`(티켓 배치를 새 서브에이전트 + 파일 기반 인계 + 이중 검토로. `implement` 배치의 컨텍스트 고갈이 friction으로 기록되면 D-014대로 벤더링).
- 재검토 조건: product-loop 승격 판정 시 진입 규칙을 재검토한다. 지정 repo 시험에서 superpowers 요소의 소비 증거(D-018 축)가 나오면 해당 요소만 승격을 검토한다. Codex가 4 체크포인트 스킬을 자동 호출하는 사례가 기록되면 어댑터 측 차단을 검토한다.

### 이유

세 스킬군이 같은 자리를 다투는 듯 보인 원인은 층위 미구분이다. D-018이 이미 product-loop를 제품 틀로, 매트 체인을 분절 삽입으로 정했고, 남은 것은 비제품 기본값, 경계 규칙, 진입 규칙의 명문화였다. 경계 사례(메뉴 앱은 UI가 있어도 D-번호 루프, hushaby는 표면이 있어도 Run, 로컬 D-대장)가 보여주듯 판별 축은 화면 유무가 아니라 측정할 사용자 행동의 존재다. "오케스트레이터 + 전문 스킬" 조합이 이상적이라는 외부 조언은 옳지만 그 오케스트레이터 자리는 이미 product-loop가 UX 게이트, 증거 규율·`LOOP.md` 상태 관리까지 갖추고 차지하고 있으며, 2026 중반 필드도 같은 형태(컨트롤러 하나 + 전문 스킬)로 수렴했다. superpowers 커뮤니티조차 "이미 CLAUDE.md에 프로세스를 인코딩한 사용자는 스킵"을 권한다. 전역 설치 대신 스코프 시험인 이유는 소비 증거(D-018 축) 없이 매 세션 설명, 라우터 주입 비용부터 지불하게 되기 때문이다.
