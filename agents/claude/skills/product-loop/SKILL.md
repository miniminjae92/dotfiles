# Product Loop

제품 개선을 한 번의 거대한 작업이 아니라 **증거가 다음 판단을 여는 한 바퀴**로 운영한다. 한 바퀴는 여러 세션에 걸쳐도 되며, 프로젝트의 `LOOP.md`가 진행 상태의 정본이다.

단계 순서와 게이트의 정본: `~/.dotfiles/agents/conventions/product-loop/STAGES.md` (Codex 구현과 공유하는 공통 개념).

Claude 전용 실험 구현이다. Codex 구현과 함께 provider-neutral 승격 대상이며, 승격은 완료된 한 바퀴에 대한 사용자 판정 뒤에 한다 (D-018).

## 시작 또는 재개

1. 저장소의 `CLAUDE.md`·`AGENTS.md`, `CONTEXT.md`, `docs/adr/`와 제품 문서를 확인한다.
2. `docs/product-loop/**/LOOP.md`에서 `status: active`인 사이클을 찾는다.
   - 하나면 그 사이클을 재개한다.
   - 없으면 새 사이클 시작을 제안하고, 사용자 승인 뒤 `~/.dotfiles/agents/conventions/product-loop/LOOP-template.md`를 복사해 `docs/product-loop/<YYYY-MM-DD>-<problem-slug>/LOOP.md`를 만든다 (D-026).
   - 둘 이상이면 가장 최근 파일을 임의 선택하지 말고 충돌을 사용자에게 알린다.
3. `current_stage`, `next_owner`, `next_action`을 읽고 지금 할 일 하나를 먼저 보여준다.
4. `STAGES.md`에서 현재 단계 절만 읽고 실행한다.

완료 기준: 활성 사이클 하나와 현재 단계 하나가 식별되고, 사용자가 해야 할 일과 에이전트가 할 일이 분리되어 있다.

## 이미 진행된 제품에 붙이기

문서, 코드가 이미 쌓인 저장소에서 처음 이 루프를 켤 때는 1단계부터 밟지 않는다. **기존 산출물을 단계에 매핑해 `LOOP.md`를 역으로 채우고**, 실제로 막혀 있는 단계를 `current_stage`로 놓는다.

- 산출물은 **옮기지 않고 기존 경로를 링크한다.** 문서 사이의 링크가 깨지지 않고 되돌리기가 싸다.
- 어느 단계에도 매핑되지 않는 문서는 그 자리에서 지우지 말고 목록으로 사용자에게 제시한다.
- 매핑했으나 게이트를 충족하는 증거가 없는 단계는 `passed`가 아니라 `in_progress`로 둔다.

완료 기준: 모든 기존 산출물이 어느 단계에 속하는지 또는 어디에도 속하지 않는지 판정됐고, 현재 막힌 단계 하나가 `current_stage`로 정해져 있다.

## 한 단계 실행

1. 환경에서 확인할 수 있는 사실은 직접 조사한다. 사용자에게는 목적, 판단, 취향, 관찰처럼 **사용자만 가진 것**을 묻는다.
2. 현재 단계의 산출물과 반증을 `LOOP.md` 또는 그 파일이 가리키는 문서에 기록한다.
3. 단계 게이트를 실제 증거로 충족했을 때만 상태를 `passed`로 바꾸고 다음 단계를 `in_progress`로 연다.
4. 게이트가 충족되지 않으면 `current_stage`를 유지하고 `next_owner`, `next_action`, `blocker`를 구체적으로 갱신한다.
5. 되돌릴 수 있는 조사, 작성, 구현, 검증은 이어서 수행한다. 다음은 사용자에게 넘긴다.
   - 인터뷰 응답, 취향 판단, Grill 답변, 프로토타입 사용 관찰
   - 이슈 게시, 배포, 데이터 삭제처럼 외부 상태를 바꾸거나 복구 비용이 큰 일
   - 측정 창이 지나야 실제 결과를 얻는 일

완료 기준: 현재 단계가 증거와 함께 통과했거나, 통과에 필요한 다음 행동의 소유자와 관찰 가능한 완료 조건이 한 개로 좁혀져 있다.

## 스킬 연결

엔지니어링 체인을 연속 실행하지 않는다. 4~5단계와 10~11단계에 나눠 꽂고, 사이의 6~9단계 게이트를 건너뛰지 않는다 (D-018).

| 단계 | 스킬 | 호출 |
|---|---|---|
| 4 Grill | `grill-with-docs` | **사용자 호출** |
| 5 PRD | `to-spec` | **사용자 호출** |
| 7 Wireframe · 8 Prototype test | `prototype` | 에이전트 |
| 10 Issues | `to-tickets` | **사용자 호출** |
| 11 구현 | `implement` | **사용자 호출** |
| 11 이후 검토 | `code-review` | 에이전트 (고정점과 PRD가 있을 때) |
| 도메인어 변경 시 | `domain-modeling` | 에이전트 (`CONTEXT.md`·`docs/adr/`에 기록) |

**사용자 호출** 표시는 모델이 스스로 실행할 수 없는 스킬이다. 그 단계에 오면 실행을 시도하는 대신, 지금 무엇을 왜 부르는지 한 줄로 설명하고 사용자에게 호출을 요청한 뒤 멈춘다.

PRD 정본은 `to-spec` 산출물 하나다. 연결된 스킬의 산출물은 `LOOP.md`에서 **링크한다** — 같은 내용을 여러 문서에 옮겨 적으면 정본이 갈라진다.

## dref 연결 (6, 9단계)

dref는 기획 원문을 UX 흐름과 UI 방향으로 구체화하고, 결과로 검증된 판단만 개인 자산으로 승격하는 도구다 (`http://127.0.0.1:4180`).

계약 — **에이전트는 제안하고 사용자가 채택한다** (dref ADR-0001):

- `ux.json`·`ui.json`은 확정된 판단만 담는 정본이다. 에이전트는 여기에 직접 쓰지 않는다.
- 제안은 `projects/<id>/proposals/<stamp>/`에 프롬프트, 제안, 채택 여부와 함께 남는다. dref 검증을 통과한 제안을 사용자가 채택해야 정본이 된다.
- 채택되지 않은 제안은 **거절 사유**를 남기고 다음 제안의 입력이 된다. 사유 없이 다시 제안하면 같은 제안이 반복된다.
- 근거로는 미검토 후보도 올릴 수 있다. 사용자가 채택하는 시점에 그 아이템의 판정이 `직접 저장`으로 바뀐다.

이 저장소의 프로젝트가 dref에 있으면 6, 9단계 산출물은 dref 프로젝트를 정본으로 삼고 `LOOP.md`는 링크만 한다. 없으면 `docs/product-loop/<사이클>/` 아래 문서로 남긴다.

취향 근거 조회는 `dref-consult`를 쓴다. (2026-07-28 우선 제외 — dref 개편 중이라 라이브러리, API가 유동적. 개편 완료 후 재연결)

## 사이클 종료

측정값과 UX 개선 가설이 기록되면 현재 사이클을 `status: completed`로 바꾼다. 가설을 다음 사이클의 최초 증거로 복사하지 말고 **링크해 출처를 보존한 뒤** 새 `LOOP.md`를 만든다.

완료 기준: 출시 여부와 무관하게 결과가 측정됐고, 다음 바퀴에서 검증할 UX 개선 가설 하나가 정해져 있다.
