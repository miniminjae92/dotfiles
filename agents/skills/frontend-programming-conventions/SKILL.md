# Frontend Programming Conventions

주석을 읽어야 이해되는 코드보다 이름, 제어 흐름, 책임 배치로 의도가 드러나는 코드를 작성한다. 변경을 이해하고 검증하는 비용을 기준으로 설계한다.

## 적용 방식

- 명시한 사용자 요구와 저장소 계약을 먼저 확인하고, 이 스킬은 빈 부분의 기본값으로 적용한다. 충돌하는 선택은 근거를 설명한다.
- 주석 최소화와 의도가 드러나는 네이밍은 사용자가 밝힌 선호다. 아래 설계 기준은 그 선호와 공식 자료를 바탕으로 구성한 기본안이며, 모두 사용자가 개별 승인한 절대 규칙으로 취급하지 않는다.
- 작업 대상의 `package.json`, 인접 코드, lint/format 설정, 테스트 실행 경로를 확인한다. 기존 JS/TS와 도구를 유지하고, 도구 교체는 현재 요구를 해결하는 데 필요할 때만 제안한다.
- 계획 요청에서는 경계, 동작, 검증 방법까지만 설계한다. 구현 요청에서는 필요한 변경과 검증을 완료한다. 이 스킬 자체가 배포나 범위 확대를 승인하지 않는다.
- React 코드에 적용할 때는 [React 기준](references/react.md)을 읽는다. 다른 프레임워크에 React의 Hook 규칙을 대입하지 않는다.

## 동작과 책임부터 정한다

코드를 나누기 전에 현재 입력, 사용자 행동, 관찰 가능한 결과를 확인한다. 상태가 문제라면 어떤 사건에서 상태가 바뀌는지와 새로고침, 화면 전환 후 유지할 값을 밝힌다. 작은 수정에 별도 설계 문서를 의무화하지 않는다.

- 정책 판단, 네트워크/저장소 접근, UI 표현 중 함께 바뀌는 책임을 찾는다. 독립적으로 판단 가능한 정책은 입력과 결과가 명확한 순수 함수로 분리할 수 있다.
- 분리의 기준은 파일 길이가 아니라 변경 이유, 상태 소유권, 호출자가 알아야 할 정보다. `App`은 화면 조합을 맡고 기능 내부 정책은 해당 기능 가까이에 둔다. 단순한 상태까지 일률적으로 추출하지 않는다.
- 같은 기능에서 함께 수정하는 코드를 가까이 배치한다. 의미가 다른 로직은 모양이 같다는 이유만으로 공통화하지 않는다.
- 새 추상화는 현재 호출자의 복잡성을 줄이거나 실제 중복 정책을 일치시킬 때 도입한다. 미래 기능만을 위한 범용 엔진, 설정 옵션, 계층은 만들지 않는다.
- 클래스, 값 객체, 디자인 패턴은 실제 불변식이나 상태 책임이 있을 때 선택한다. Java 객체지향 생활체조의 줄 수 제한, getter 금지, 원시값 포장 등을 프론트에 기계적으로 이식하지 않는다.

## 이름과 코드로 읽히게 한다

- 변수와 함수는 도메인 용어와 의도를 드러낸다. `data`, `flag`, `process`처럼 맥락을 숨기는 이름은 더 구체화한다. 불리언은 `is`, `has`, `can`, `should` 등으로 질문이 읽히게 한다.
- 조회처럼 보이는 함수에 저장, 분석 이벤트, 상태 변경을 숨기지 않는다. 반환 타입과 실패 표현은 같은 역할의 함수끼리 일관되게 유지한다.
- 복잡한 조건에는 의미 있는 이름을 붙이고, 중첩 조건과 삼항 연산자는 위에서 아래로 읽히는 분기로 풀어낸다. 간단한 두 가지 JSX 표현에는 삼항 연산자를 사용할 수 있다.
- 업무 의미가 있는 문자열과 수치는 이름을 부여한다. 한 번 쓰는 자명한 값까지 상수 파일로 이동하지 않는다.
- 객체와 배열의 변경은 소유권을 확인한다. 호출자가 넘긴 값이나 React state를 직접 변경하지 않는다.
- TS에서는 정상 상태와 실패 상태를 구분할 수 있는 타입을 사용한다. 외부 데이터는 타입 선언만으로 검증됐다고 간주하지 않는다. 타입 단언이나 `any`로 계약의 불일치를 감추지 않는다.
- export 방식, 파일명 형식, 세미콜론 등 기계적 스타일은 저장소 규칙을 따른다. 이번 변경과 관계없는 스타일 통일을 하지 않는다.

## 주석은 코드에 없는 이유를 담는다

먼저 이름이나 구조로 설명할 수 있는지 검토한다. 줄별 해설, 조건문의 한국어 번역, 변경 이력은 주석에 반복하지 않는다.

남길 가치가 있는 주석은 외부 시스템 제약, 제거 조건이 있는 우회 처리, 코드만으로 복원하기 어려운 의도와 불변식이다. 해당 코드 가까이에 짧게 적고, 동작을 바꿀 때 함께 검증한다. 긴 사건 경위와 선택 기록은 작업 기록이나 Git 이력에 둔다. 주석의 주장도 현재 코드와 증거로 확인한다.

## 사용자에게 보이는 경계까지 다룬다

- 버튼, 링크, 입력은 의미에 맞는 HTML 요소를 사용한다. 입력 label, 아이콘 버튼의 접근 가능한 이름, 키보드 조작과 포커스를 확인한다. 모달은 열기와 닫기뿐 아니라 포커스 이동과 복귀를 다룬다.
- 비동기 작업은 필요한 로딩, 성공, 빈 결과, 실패 상태를 구분한다. 중복 제출, 늦은 응답, 재시도의 처리 방식은 실제 흐름에 맞게 정한다. 실패를 숨기는 빈 `catch`는 의도한 fallback과 관찰 방법이 있을 때만 허용한다.
- localStorage 같은 영속 데이터는 유효 범위와 만료, 누락, 파싱 실패를 고려한다. 클라이언트 저장값이 서버의 권한이나 확정 상태를 대신한다고 가정하지 않는다.
- 기능 종료나 비활성화 조건은 저장된 값, 강제 표시, 서버 응답 등 다른 경로와의 우선순위를 명시한다. UI 숨김과 서버의 기능 중단은 별개 계약이다.
- 레이아웃을 바꾸면 관련 화면 크기와 긴 텍스트, overflow를 브라우저에서 확인한다. 성능 최적화는 측정된 병목이나 명확한 비용을 근거로 한다.

## 테스트는 동작을 보호한다

먼저 무엇이 실패하면 사용자에게 문제가 되는지 적고, 그 계약을 가장 저렴하게 관찰할 수 있는 수준을 선택한다. 모든 컴포넌트나 Hook마다 테스트 파일을 만드는 것이 목표는 아니다.

| 검증 대상 | 적절한 시작점 |
| --- | --- |
| 입력에 따른 정책, 변환, 경계값 | 순수 함수 단위 테스트 |
| 클릭, 입력, 비동기 응답 후 UI 변화 | 컴포넌트와 실제 상태 제어를 함께 검증하는 통합 테스트 |
| 새로고침, 라우팅, 브라우저 저장소, 핵심 사용자 여정 | 필요한 최소 브라우저/E2E 테스트 |

- 버그 수정은 재현 조건에서 실제 잘못된 동작 때문에 실패하고 수정 후 통과하는 회귀 테스트를 우선한다. 도구 부족 등으로 자동화하지 못한 부분은 재현 절차와 미검증 범위를 남긴다.
- 보존해야 할 동작을 바꾸지 않는 리팩터링은 기존 테스트와 필요한 보완 테스트로 확인한다. 일부러 실패하는 테스트를 만들 필요는 없다.
- 정책 함수만 맞아도 호출자가 그 함수를 우회하면 버그가 남는다. 버그가 발생한 실제 분기와 UI 연결을 검증한다.
- 사용자에게 보이는 텍스트, role, 접근 가능한 이름, 결과를 검증한다. 내부 setter 호출 횟수, private 함수, 전체 DOM snapshot에 계약을 의존시키지 않는다.
- 네트워크, 시간 등 외부 경계만 필요에 따라 대체한다. 검증 대상의 상태 제어까지 mock해 테스트가 정답을 직접 만들어 내게 하지 않는다.
- 기존 테스트 도구를 우선 사용한다. 필요한 DOM/브라우저 검증을 현재 도구가 못 하면 공백과 대안을 설명한다. 임의 sleep 대신 완료 조건을 기다린다.

## 완료 판단과 설명

변경한 동작, 책임 배치의 이유, 실행한 검사와 결과, 남은 검증 공백을 짧게 보고한다. 관련 테스트와 저장소 필수 검사를 실행하되, 빌드 성공을 브라우저 동작 확인으로 표현하지 않는다. 리뷰 요청이면 영향 있는 발견을 코드 위치와 재현 조건으로 설명하고 스타일 취향과 구분한다.

사용자가 이해를 요청하면 현재 소스의 값과 호출 흐름으로 설명한다. 객체, 프로퍼티, state, Hook 등 표준 용어를 사용하고 낯선 프론트 개념만 처음에 정의한다. 설명용 예시는 실제 코드와 명확히 구분한다.

## 기준의 근거

세부 판단이 필요하거나 기준을 개정할 때 아래 원문을 참고한다. 이 스킬은 개인 작업 기준이며 우아한테크코스의 공식 평가표가 아니다.

- [Toss Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/): 가독성, 예측 가능성, 응집도, 결합도의 균형.
- [Testing Library 원칙](https://testing-library.com/docs/guiding-principles/): 사용 방식에 가까운 관찰 가능한 테스트.
- [Playwright 모범 사례](https://playwright.dev/docs/best-practices): 브라우저 테스트의 사용자 관점, 격리, 안정적인 대기.
- React 상태와 Effect의 근거는 [React 기준](references/react.md)에 연결한다.
