# React 기준

React의 상태 소유권, 렌더링, 외부 동기화를 변경할 때 적용한다. 저장소의 React 버전과 기존 데이터 조회 방식을 먼저 확인한다.

## 상태의 소유권과 수명

- props나 기존 state에서 계산할 수 있는 값은 렌더링 중 계산한다. 복사한 state를 Effect로 계속 맞추는 구조를 피한다.
- 상태는 필요한 소비자들의 가장 가까운 적절한 공통 조상에 둔다. 상태를 옮길 때 화면 전환, 조건부 렌더링, `key` 변경으로 언제 초기화되는지 확인한다.
- 서로 배타적인 화면 상태가 여러 불리언 조합으로 모순을 만들면 하나의 status나 reducer를 고려한다. 독립적인 불리언까지 하나로 합치지 않는다.
- 모듈 최상위 가변 변수는 컴포넌트 인스턴스 간 공유된다. 인스턴스에 속하고 렌더링에 필요한 값은 state, 렌더링에 필요 없는 지속 값은 ref를 검토한다. 애플리케이션 전체 중복 방지는 별도 수명 요구로 판단한다.
- props는 상태와 필요한 동작을 드러내는 작은 인터페이스로 만든다. 기능 내부 상태를 호출자가 알아야만 사용할 수 있는 setter 묶음은 책임 분리를 재검토한다.
- 컴포넌트는 UI 단위, custom Hook은 상태를 사용하는 동작 단위, 순수 함수는 입력을 결과로 바꾸는 계산 단위로 나눈다. custom Hook 호출마다 상태가 독립적이라는 점을 고려한다.
- Hook으로 옮기는 것만으로 책임이 분리됐다고 판단하지 않는다. 호출자가 알아야 할 내부 상태가 줄었는지, 관련 로직이 함께 바뀌는지 확인한다.

## 렌더링, 이벤트, Effect

| 수행하려는 일 | 기본 위치 |
| --- | --- |
| props/state로 화면에 필요한 값 계산 | 렌더링 중 계산 |
| 클릭, 제출 등 특정 사용자 행동에 반응 | 이벤트 핸들러 |
| 현재 상태를 네트워크, 구독, DOM 등 외부 시스템과 동기화 | 프레임워크의 데이터 기능이나 필요한 Effect |

- 렌더링은 순수하게 유지한다. 렌더링 중 네트워크 요청, 저장소 쓰기, 분석 이벤트 전송을 실행하지 않는다.
- 일반적인 `useState`, `useEffect` 등 Hook은 컴포넌트나 custom Hook의 최상위에서 일관된 순서로 호출한다. 조건부 실행이 필요하면 조건을 Effect 안이나 자식 컴포넌트 경계로 옮긴다.
- Effect의 의존성은 실제 읽는 반응형 값을 반영한다. `[]`를 원하는 실행 횟수를 맞추는 도구로 사용하지 않는다. 불필요한 의존성이 생기면 먼저 Effect의 책임과 코드를 조정한다.
- `[]`는 애플리케이션 전체에서 단 한 번이라는 보장이 아니다. 재마운트와 개발 Strict Mode의 setup/cleanup 반복을 견딜 수 있게 설계한다.
- 구독, 타이머에는 대응하는 정리를 둔다. 비동기 요청은 필요에 따라 취소하거나 오래된 결과를 무시해 이전 응답이 최신 상태를 덮지 않게 한다. 단순한 mounted 확인만으로 요청 간 경합까지 해결됐다고 보지 않는다.
- Hook 의존성 경고를 무시하거나 ref 플래그로 Effect 재실행을 막기 전에, 반복 실행에 안전해야 하는 동작인지와 수명 요구를 확인한다.
- 데이터 조회는 저장소가 사용하는 프레임워크나 라이브러리의 캐시, 오류, 취소 기능을 우선 활용한다. 작은 수정을 위해 새로운 상태 관리 라이브러리를 추가하지 않는다.
- `useMemo`, `useCallback`, `memo`는 정확성을 위한 장치가 아니다. 측정한 비용이나 참조 안정성의 실제 필요가 있을 때 도입한다.

## 분리 작업의 확인 질문

상태와 Effect를 옮겼다면 다음 중 변경에 해당하는 것을 확인한다.

- 기존 state가 같은 기간 유지되는가? 필터 변경이나 재마운트로 입력, 발급 결과 등이 사라지지 않는가?
- 비활성화 정책이 저장된 값이나 늦은 서버 응답으로 우회되지 않는가?
- 사용자 행동 한 번이 중복 요청이나 의도하지 않은 이벤트를 만들지 않는가?
- 새 책임 단위가 오류와 cleanup까지 소유하는가, 아니면 호출자에게 다시 떠넘기는가?
