# Korean Review Comments

작성자가 선택의 이유를 설명하고 함께 판단할 수 있는 한국어 리뷰 코멘트를 쓴다. 분석 결과에서 상대에게 건넬 말을 고르는 작업이며, 보고서의 어미만 바꾸는 작업이 아니다.

## 입력과 근거

- 리뷰 결과, 대상 코드, 요구사항, PR 설명과 기존 대화에서 필요한 맥락을 읽는다. [code-review의 근거 전달 기준](../code-review/SKILL.md#5-다음-판단에-필요한-근거-남기기)에 따라 사실, 영향, 미확인 조건, 선택의 비교가 충분한지 확인한다. 입력 형식 자체를 요구하지는 않는다.
- 위치나 근거가 부족하면 접근 가능한 코드와 테스트에서 해당 사실을 보충한다. 본격적인 분석이 필요하면 `code-review`로 돌아가 해당 범위만 검토한다. 접근할 수 없다면 확인이 필요한 지점은 사용자에게 따로 알리고, 근거가 충분한 코멘트부터 작성한다.
- 사용자가 이미 전하려는 요점을 말했다면 그 뜻을 보존한다. 문장을 자연스럽게 만들려고 새로운 설계 지적이나 감상을 보태지 않는다. 근거와 충돌하면 먼저 그 차이를 알린다.
- 질문의 용어나 범위가 여러 뜻으로 읽혀 답이 달라진다면, 코드와 대화에서 가리키는 대상을 먼저 확인한다. 자료로 해소되지 않을 때는 가능한 뜻을 구체적으로 짚어 확인한 뒤 판단한다.
- 코멘트만 요청받았는데 전체 저장소를 다시 리뷰하거나 제품 코드를 수정하지 않는다.
- 첫 초안을 쓰기 전에 [실제 게시 사례](references/cases.md)의 해당 유형을 읽는다. 말투나 질문과 답변의 맥락이 더 필요하면 [우테코 대화 색인](references/woowacourse/index.md)에서 관련 PR을 골라 읽는다. 사용자의 표현은 본인 발언에서, 상대방의 반응과 대화 방식은 전체 대화에서 참고한다.

## 전할 말 고르기

초안을 쓰기 전에 다음 순서로 판단한다.

1. 이 발견을 전달하면 작성자가 무엇을 판단하거나 확인할 수 있는지 정한다. 필수 수정은 포함하고, 이번 변경과 관련이 약하거나 다른 코멘트와 겹치는 내용은 제외한다.
2. 전달 목적을 정한다. 확인된 오류의 수정 요청, 선택의 이유를 듣는 질문, 선택 가능한 개선 제안, 의미 있게 본 구현에 대한 반응을 구분한다. 이 내부 분류를 댓글의 제목이나 라벨로 나열할 필요는 없다.
3. 해당 코드 옆에서 작성자에게 직접 말한다는 전제로 새로 쓴다. 질문의 이유나 수정 필요성을 이해하는 데 필요한 관찰과 근거를 남긴다.

작성자가 현재 구현을 유지할 이유를 듣고 싶은 경우에는 질문한다. 리뷰어가 특정 변경을 권하는 경우에는 자신의 제안임을 밝히고 이유를 설명한다.

### 설계 선택과 변경 제안

- 실제 코드의 선택과 그 선택이 영향을 주는 상황을 짚고, 어떤 기준이나 제약으로 결정했는지 묻는다. 현재 구조를 유지할 합리적인 이유도 들을 수 있어야 한다.
- 질문은 답에 따라 리뷰어의 판단이 달라질 때 한다. "분리하는 게 더 좋지 않을까요?"처럼 결론을 정해 놓고 동의를 구하기보다, 현재 배치에서 고려한 책임이나 변경 범위를 묻는다.
- 대안을 비교할 이유가 있다면 리뷰어가 걱정하는 점도 함께 드러낸다. 질문 뒤에 정답을 숨긴 채 맞히게 하거나, 원칙 이름만 던져 설명을 시험하지 않는다.
- 선택의 이유를 확인하는 단계라면 그 답을 받는 데서 코멘트를 마친다. 답변 전에 테스트 추가나 구조 변경을 새 의무로 붙이지 않는다. 분석에서 선택 사항으로 남긴 대안은 코멘트에서도 선택 사항으로 표현한다.
- 후속 리뷰는 앞선 질문과 답변, 실제 변경을 함께 읽고 해결된 점과 남은 쟁점을 구분한다. 설명으로 의문이 풀렸으면 같은 이유를 다시 묻지 않는다. 다른 해결책을 택했더라도 최초 우려가 해소됐는지로 판단하고, 미해결이라면 아직 깨지는 조건을 구체적으로 짚는다.
- 한 코멘트에서는 한 판단에 집중한다. 답변에 필요한 맥락은 제공하되 질문을 연달아 붙여 심문처럼 만들지 않는다.

### 확인된 문제와 잠재적 위험

- 확인된 오류는 발생 조건과 실제 결과, 어긴 계약을 먼저 명확하게 설명한다. 수정이 필요하다는 사실은 유지하고, 해결 방법에 선택지가 있을 때 그 판단을 묻는다. 모든 코멘트를 의문문으로 끝낼 필요는 없다.
- 잠재적 위험은 확인하지 못한 조건을 코멘트 안에서도 남긴다. 조건이 성립할 때의 영향과 무엇을 확인하려는지 함께 말한다.
- 테스트나 재현을 직접 실행했다는 표현은 실제 실행 기록이 있을 때만 쓴다.

### 긍정적 의견

실제 구현에서 좋게 본 선택과 그 효과를 구체적으로 짚는다. "기존 컨트롤러를 수정하지 않고 실행 결과를 연결할 수 있다"처럼 무엇이 유지되거나 쉬워졌는지 드러나면 충분하다. 미션의 목적이나 일반 원칙에 대한 설명은 그 선택의 의미를 이해하는 데 필요할 때만 덧붙인다.

좋아 보이는 선택도 그 기준이 궁금하면 질문할 수 있다. 이미 코드와 설명으로 이유가 충분하다면 감상으로 마쳐도 된다. 칭찬마다 질문을 붙이지 않는다. 작성자가 깊이 고민했다거나 개념을 이해했다는 내면의 평가는 확인된 대화 없이 단정하지 않는다.

## 한국어로 다듬기

한국어 표기와 명료함은 `/Users/miniminjae/.obsidian/mimir/20 Knowledge/좋은 글 작성 기준.md`를 따른다. 사용자 명의의 말투는 같은 디렉터리의 `목소리와 어조 기준.md`를 참고한다. 다만 이 스킬의 합의된 목적은 선택의 근거를 함께 살피는 대화다. 일반 설득 글의 주장, 반박, 접는 조건, 기한을 붙인 조치 요청 규칙과 충돌하면 이 스킬의 대화 목적을 우선한다. 정중함과 근거에 맞는 확신은 유지한다.

- 사용자의 실제 코멘트와 요청한 말투를 따른다. 이 사용자의 리뷰에서는 해요체와 합니다체를 함께 쓰고, 문장의 역할에 따라 어미와 부호의 강약을 바꾼다. 일반 글쓰기 기준의 종결어미 통일보다 이 리뷰 말투를 우선한다.
- 코드 설명 뒤에 "좋았습니다"를 붙이는 데 그치지 말고, 무엇을 의미 있게 봤는지 말한다. "좋은 점", "개선 제안, 중요도 보통" 같은 분석 라벨은 저장소 규칙이나 사용자 요청이 있을 때만 댓글에 넣는다.
- 기술 용어는 구체적인 판단에 필요할 만큼 쓴다. "변경 용이성을 확보합니다"보다 무엇이 함께 바뀌는지 말하고, 이미 이름 붙은 클래스나 메서드는 정확히 지칭한다.
- 코멘트가 놓일 코드와 기존 대화를 고려해 충분한 맥락만 남긴다. 앞선 대화를 못 봐도 발생 조건과 요청을 오해하지 않아야 한다.
- 작성자에게 실제로 할 말이 끝나면 멈춘다. 같은 길이의 문단이나 정해진 문장 수를 맞추지 않는다.

### 문장의 역할에 따른 어미와 부호

사용자가 선택한 말투 기준이다. 아래 표현은 역할별 선택지이며, 한 코멘트에 전부 넣거나 일정 비율로 배합하는 형식이 아니다.

| 문장의 역할 | 어미와 부호의 사용 |
|---|---|
| 발견한 점에 반응 | "잘 드러나네요!", "좋네요~!"처럼 `네요`, `!`, `~!`로 반응의 온기를 표현한다. |
| 관찰과 근거 설명 | "직접 알고 있네요.", "이동하게 되더라고요."처럼 차분하게 설명한다. |
| 판단을 정리 | "좋았습니다.", "필요하다고 생각합니다."처럼 합니다체로 의견을 분명하게 전달한다. |
| 생각을 요청 | "어떻게 생각하시나요?"처럼 의문문에는 `?`를 사용해 상대에게 답할 차례를 넘긴다. |
| 궁금함을 표현 | "판단 기준이 궁금합니다!"처럼 합니다체에 `!`를 붙여 관심을 표현할 수도 있다. |

설명은 차분하게 두고 반응과 관심에는 온기를 준다. "좋았습니다!"처럼 합니다체와 느낌표도 함께 쓸 수 있다. 사실의 확실성이나 수정 필요성은 어미와 부호의 강약으로 바꾸지 않는다. 구체적인 관찰이나 감상 없이 부호만 덧붙이지 않는다.

## 출력과 마무리

인라인 코멘트는 파일, 줄 번호, 대상 코드와 바로 게시할 본문을 함께 제공한다. 구체적인 칭찬, 질문, 수정 제안은 해당 코드에 배치한다.

최종 리뷰 본문은 전체 판단, 필요한 검증 요약, 남은 조치를 짧게 전달한다. 인라인에서 설명한 구현 세부사항은 반복하지 않는다.

코멘트만 요청받으면 전달용 결과물을 먼저 제공한다. 게시 여부를 판단하는 데 필요한 주의사항은 코멘트 밖에 구분한다. 로컬 절대 경로, 워크트리 생성 내역, 내부 분석 분류도 공개 댓글 본문 밖에 둔다. 전달할 내용이 없으면 억지 초안 대신 그 이유를 짧게 알린다.

최종 확인:

- 설계 질문은 현재 선택을 유지하는 답도 받아들일 수 있고, 왜 묻는지 구체적인 맥락이 있는가?
- 코드나 기존 대화로 확인할 수 있는 사실을 작성자에게 떠넘기지 않았는가?
- 확인된 오류의 조건과 영향, 미확인 위험의 불확실성이 원래 분석과 같은가?
- 좋은 점에는 리뷰어가 의미 있게 본 이유가 있고, 작성자의 생각을 지어내지 않았는가?
- 작성자가 무엇을 설명하거나 조치하면 되는지 알 수 있는가?

수정 결과를 검증할 때는 [사례와 검증 기준](references/cases.md)의 실패 사례도 함께 사용한다. 규칙을 추가하거나 바꿀 때는 [규칙별 대화 근거](references/evidence.md)를 확인한다. 실제 사례의 관찰, 근거, 질문을 연결하는 방식을 참고하되 문장을 상용구로 복제하지 않는다.

결과는 기본적으로 초안이다. 게시 요청이 명시된 경우에만 지정된 대상에 게시하고, 승인이나 변경 요청 같은 리뷰 상태 변경은 별도 행동으로 구분한다.
