# 사례와 검증 기준

실제 게시 사례와 검증용 가상 사례를 구분한다. 실제 사례는 사용자가 참고 대상으로 선택한 우테코 대화에서 가져왔다. 과거 발언의 모든 표현과 기술 판단이 현재의 정답은 아니다. 문장 일치가 아니라 사실 보존, 질문의 목적, 요청의 명확성으로 판단한다. 다른 미션의 본인과 상대방 질문, 답변, 리뷰 본문은 [전체 대화 색인](woowacourse/index.md)에서 찾는다.

## 1. 실제 게시: 관찰에서 선택의 기준으로 이어지는 질문

출처: [java-mvc #1186, 본인 코멘트](https://github.com/woowacourse/java-mvc/pull/1186#discussion_r4181598909). [전체 대화](woowacourse/prs/java-mvc-1186.md)에서 상대방의 답변까지 확인할 수 있다.

> `AnnotationHandlerMapping`의 로직을 작은 메서드들로 잘 분리해주셔서 각 메서드의 역할은 이해하기 좋았습니다!
>
> 다만 메서드의 배치 순서는 조금 고민해볼 수 있을 것 같아요. 외부에서 사용하는 `initialize()`와 `getHandler()`가 떨어져 있고, `initialize()`에서 이어지는 호출 흐름도 코드의 배치 순서와 조금 달라서 읽으면서 이동하게 되더라고요.
>
> 루디는 메서드의 배치 순서를 정할 때 어떤 기준을 사용하셨는지 궁금합니다!

참고할 점: 실제로 읽으며 겪은 이동을 설명하므로 왜 묻는지 알 수 있다. 상대방은 기능 분리에 집중하면서 배치 순서를 놓쳤다고 답했고, 공개 메서드와 호출 흐름을 기준으로 정리하겠다고 설명했다. 메서드 순서의 단일 정답이나 칭찬으로 시작하는 고정 형식으로 일반화하지 않는다.

같은 PR의 두 사례도 구분해서 읽는다.

- [경계 상황 확인 제안](https://github.com/woowacourse/java-mvc/pull/1186#discussion_r4181536884): 클래스 경로가 `/`인 구체적인 상황을 제시했다. 오류가 이미 확인된 새 상황에서는 확인 요청만으로 수정 필요성을 흐리지 않는다.
- [private 메서드 허용 기준 질문](https://github.com/woowacourse/java-mvc/pull/1186#discussion_r4181565211): 대안을 언급하고 판단 기준을 물었다. 답변에서는 의도적인 허용이 아니었음이 드러났다. 과거의 "고려해주신 점"이라는 표현까지 복제해 작성자의 의도를 추정하지 않는다.

## 2. 가상 사례: 확인된 오류 알리기

입력: 재고 1개에 동시 주문 2개를 넣은 테스트에서 둘 다 성공했다. 다른 직렬화 장치는 없다. 요구사항은 재고보다 많은 주문을 허용하지 않는다. 수정 방법은 아직 정하지 않았다.

후보:

> 재고가 1개일 때 주문 두 개를 동시에 보내니 둘 다 성공했어요. 재고보다 많은 주문이 확정돼서 이 경우는 수정이 필요해요. 재고 확인과 차감 사이에 다른 주문이 들어오는 상황을 어떻게 막으면 좋을까요?

확인: 재현했다는 근거가 있을 때만 첫 문장을 쓴다. 수정 필요성을 취향으로 낮추지 않고, 락 등 특정 해결책을 정답으로 강제하지 않는다.

## 3. 실제 게시: 구체적인 선택에 대한 짧은 긍정적 반응

출처: [java-http #1213, 본인 코멘트](https://github.com/woowacourse/java-http/pull/1213#discussion_r4060093814). [전체 대화](woowacourse/prs/java-http-1213.md).

> Content-Length를 문자열 길이가 아닌 UTF-8 바이트 길이로 계산해 실제 전송 크기와 일치시킨 점, 저도 배워가네요~!

참고할 점: 구현의 선택과 의미가 한 문장에 들어 있다. 미션 목적을 다시 설명하거나 질문을 덧붙이지 않아도 충분하다. "저도 배워가네요"라는 반응이나 문장부호를 모든 칭찬에 복제하지 않는다.

## 4. 실제 작성 과정의 실패: 재현을 수정 의무로 승격하기

출처: java-mvc #1234 리뷰 초안 작성 대화. 아래는 게시된 GitHub 코멘트가 아니라 에이전트가 제안했다가 사용자의 질문을 받고 제외한 의견이다.

입력: 미션은 Legacy MVC와 어노테이션 MVC의 공존이다. 일반 로그인과 회원가입 흐름은 정상이다. 임시 테스트에서 `PROPFIND /`는 변경 전 forward, 변경 후 enum 변환 예외로 동작이 달랐다. PROPFIND 지원이나 기존 forward 동작을 보장한다는 계약은 확인하지 못했다.

실패한 초안은 다음 매핑을 조회하도록 수정하라고 권했다. 이를 "다음 HandlerMapping을 조회하도록 하는 게 좋지 않을까요?"로 바꿔도 특정 해결책에 동의를 구하는 제안일 뿐이다.

확인: 재현한 동작 차이와 요구사항 위반을 구분한다. 일반 흐름에 영향이 없고 지원 계약도 없으므로 이 사례는 게시 코멘트에서 생략한다. 다른 입력에서 지원 계약이나 실제 영향이 확인되면 다시 판단한다. 정확한 계약 검증은 `code-review`의 책임이며 여기서는 근거보다 강한 수정 요청으로 바꾸지 않는지 검증한다.

## 5. 가상 사례: 작성자가 이미 이유를 설명한 경우

입력: 두 매핑을 순서대로 조회하는 코드의 PR 설명에 "중복 경로는 신규 어노테이션 구현이 우선하도록 해 점진적으로 이전한다"고 적혀 있다.

확인: 순서를 정한 이유를 다시 묻지 않는다. 그 설명으로 의문이 풀렸다면 질문을 생략한다. 다른 우려가 실제로 남아 있을 때만 그 상황을 논의한다.

## 6. 가상 사례: 아직 확인되지 않은 위험

입력: 캐시 갱신이 동시에 실행되면 최신 값이 오래된 값으로 덮일 수 있는 경로를 확인했다. 호출을 한 번에 하나로 제한하는 운영 설정은 확인하지 못했다.

후보:

> 갱신 두 개가 겹치면 늦게 끝난 이전 요청이 최신 값을 덮을 수 있어 보여요. 운영에서 갱신을 한 번에 하나만 실행하도록 제한하고 있나요?

확인: 운영 설정을 직접 확인할 수 있으면 먼저 확인한다. 실제 데이터 손상이 일어났다고 쓰거나 테스트를 실행했다고 꾸미지 않는다. 작성자의 답에 따라 결함 여부를 판단할 수 있어야 한다.

## 7. 가상 사례: 같은 단어가 다른 대상을 뜻하는 경우

입력: 작성자는 "에러 응답 code를 어디까지 제공할지" 물었다. 코드에는 HTTP 상태와 JSON의 문자열 `code` 필드가 모두 있다. PR 본문만으로 어느 쪽을 말하는지 확정할 수 없다.

확인: HTTP 상태 코드의 정책을 길게 설명하기 전에 HTTP 상태와 JSON의 `code` 중 무엇을 뜻하는지 확인한다. 코드나 본문에 이미 뜻이 명시됐다면 확인 질문을 생략하고 그 대상을 다룬다.

## 8. 가상 사례: 다른 대안으로 최초 우려가 해소된 후속 리뷰

입력: 앞선 리뷰의 문제는 private 메서드가 Handler로 등록되어 실행 시 접근 예외가 난다는 것이었다. 리뷰어는 public 메서드를 조회하는 API를 대안으로 언급했다. 작성자는 직접 선언된 메서드만 다루기 위해 기존 API를 유지하고 public 필터를 추가했다. 변경 코드와 테스트에서 private 메서드가 제외됨을 확인했다.

확인: 다른 API를 사용하지 않았다는 이유로 같은 수정을 다시 요구하지 않는다. 접근 예외 우려가 해소됐음을 판단한다. 상속 메서드 지원은 현재 요구사항에 없으므로 새 의무로 붙이지 않는다.

## 검증 실행

스킬을 개편할 때 사례의 입력만 주고 코멘트를 작성하게 한 뒤 위 기준과 대조한다. 별도 평가자를 사용할 때는 해당 평가 문제의 후보 문장과 기대 판정을 제공하지 않는다. 실제 게시 사례는 학습용으로 읽되, 출력이 원문과 같은지로 채점하지 않는다.

- 4번 상황을 필수 수정이나 합의된 지원 요구사항으로 만들지 않는가?
- 실제 결함인 2번 상황은 수정 필요성을 유지하는가?
- 구체적인 칭찬에는 인라인 위치가 붙고, 최종 리뷰에서는 같은 세부 설명이 반복되지 않는가?
- 선택의 이유를 묻는 질문과 리뷰어가 권하는 변경 제안이 구분되는가?
- 본인과 상대방의 발언, 실제 게시 원문과 새 초안이 구분되는가?

`code-review`와의 연결은 작은 실제 변경을 먼저 분석하고 그 결과를 다음 단계에 넘겨, 위치와 조건, 불확실성이 유지되는지도 확인한다. 구조 검증 통과를 문체에 대한 사용자 승인으로 해석하지 않는다.
