# 객체지향 생활체조: Java 설계 기준

Java 객체지향 설계·구현·리팩터링·리뷰에서 적용한다. 사용자는 객체지향 생활체조를 **기본 설계 기준으로 적용하고 예외는 근거를 설명**하는 방식을 선택했다. 미션이나 기존 프로젝트의 더 구체적인 규칙이 있으면 그 범위도 확인한다. 검토 요청에서 스타일 위반을 발견했다고 곧바로 코드를 수정하지 않는다.

## 원전과 적용의 구분

Jeff Bay의 Object Calisthenics는 작은 프로젝트에서 엄격한 제약을 연습한 뒤 설계 지침으로 활용하는 접근을 제안한다. 아래 아홉 항목은 원전의 규칙을 짧게 번역한 것이다. 뒤의 적용 지침과 예외 판단은 사용자의 Java 작성 기준에 맞춘 이 스킬의 해석이며 저자의 문장을 옮긴 것이 아니다.

출처: [Jeff Bay, Object Calisthenics 원문 PDF 사본](https://www.bennadel.com/resources/uploads/2012/ObjectCalisthenics.pdf), 규칙 목록 PDF 1~2쪽. 파일에 저자와 원래 배포 주소가 명시되어 있다. 크기 기준은 6쪽에서 확인했다. 웹 조회일: 2026-10-07.

1. 메서드 안의 들여쓰기는 한 단계로 제한한다.
2. `else`를 사용하지 않는다.
3. 원시값과 문자열을 객체로 감싼다.
4. 일급 컬렉션을 사용한다.
5. 한 줄에 점 하나만 사용한다.
6. 이름을 축약하지 않는다.
7. 모든 구성 요소를 작게 유지한다. 원전의 연습 기준은 클래스 50줄, 패키지 10개 파일 이내다.
8. 클래스의 인스턴스 변수를 두 개 이하로 제한한다.
9. getter, setter, property를 사용하지 않는다.

## 기본 설계 기준으로 적용하기

아래는 코드 변경 여부를 판단하는 기준이다. 규칙을 검사하는 것만으로 작업 범위를 넓히지 않는다. 현재 선택한 계약과 변경 diff에 적용하고, 기존 프로젝트 전체를 자동으로 재작성하지 않는다.

| 규칙 | Java 코드에서 확인할 것 | 피해야 할 형식적 수정 |
|---|---|---|
| 들여쓰기 | 중첩된 조건과 반복이 여러 책임이나 추상화 수준을 섞는지 살핀다. 의미 있는 행동으로 나누거나 guard clause를 검토한다. | 줄 수만 줄이려고 익명 lambda·stream 안으로 중첩을 숨기는 수정 |
| else | 조기 반환, 조건 판단의 소유 객체, 실제 변형이 있는 경우 다형성으로 분기를 단순화한다. | 단순한 두 갈래 처리를 없애려고 필요 없는 전략 클래스들을 만드는 수정 |
| 원시값·문자열 | 식별자, 경로, 금액처럼 의미·검증·불변식이 있는 값을 값 객체로 표현하는 방향을 우선 검토한다. | 한 번 쓰는 반복 인덱스나 외부 API의 모든 문자열까지 근거 없이 포장하는 수정 |
| 일급 컬렉션 | 집합의 등록·중복·검색·정렬 책임을 컬렉션 객체 안에 모을 수 있는지 확인한다. 컬렉션 자체의 가변 상태를 외부에 노출하지 않는다. | 조회 한 번을 위임하는 빈 래퍼만 추가하거나 내부 가변 컬렉션을 그대로 반환하는 수정 |
| 점 하나 | 다른 객체의 내부를 연쇄 탐색해 판단하고 있으면 필요한 행동을 소유 객체에 요청한다. | 체인을 지역 변수로 나누어 결합은 그대로 두고 점 수만 줄이는 수정 |
| 축약 금지 | 클래스·메서드·변수 이름이 책임과 도메인 의미를 나타내도록 한다. | 공인 도메인 용어·외부 API 이름까지 억지로 풀어 쓰는 수정 |
| 작은 구성 요소 | 메서드·클래스·패키지가 응집된 행동을 담는지 검토한다. 원전의 수치는 크기 점검 신호로 사용한다. | 줄 수를 맞추려고 한 책임을 여러 무의미한 파일로 나누는 수정 |
| 변수 두 개 이하 | 함께 유지할 상태와 다른 역할의 의존성을 구별하고, 클래스가 여러 책임을 섞는지 살핀다. | 필드 수만 맞추는 무의미한 묶음 객체를 만드는 수정 |
| getter/setter 금지 | 값을 꺼내 외부에서 판단·변경하는 대신 상태를 가진 객체에 행동을 요청한다. 내부 가변 상태와 불변식을 보호한다. | getter를 `value()`로 이름만 바꾸거나 DTO/렌더링/표준 인터페이스의 필요한 조회까지 기계적으로 제거하는 수정 |

특히 다음을 구분한다.

- 도메인 객체의 내부 탐색과 Stream·builder·테스트 DSL의 체인은 의미가 다를 수 있다. import나 한정 타입 이름의 점을 설계 결함으로 세지 않는다.
- 조회 메서드가 있다는 사실만으로 책임 위반이라 단정하지 않는다. 반환값의 목적, 가변 상태 노출, 행동이 다른 객체로 흩어지는지를 본다. record accessor도 같은 관점으로 판단한다.
- 외부 API가 요구하는 원시값/문자열/조회 메서드는 경계에서 유지할 수 있다. 도메인 불변식을 어느 객체에서 보장할지는 별도로 확인한다.
- 사용자가 엄격한 연습을 명시하면 그 작업에서 규칙을 제약으로 적용한다. 기본 모드의 예외를 자동 적용하거나 목표를 몰래 완화하지 않는다. 외부 인터페이스와 충돌하는 항목은 구체적으로 설명한다.

## 구현·리뷰에 적용하기

1. 선택한 계약과 책임을 먼저 확인한다. 스타일 규칙으로 새 기능 요구를 만들지 않는다.
2. 리팩터링 전에 기존 동작의 테스트를 확인하고, 변경 후 같은 동작이 보존되는지 검증한다. 새 행동을 구현할 때는 프로젝트의 테스트 절차를 따른다.
3. 현재 변경 범위 안에서 책임·캡슐화를 개선하는 방향으로 생활체조를 적용한다.
4. diff에서 위반을 발견하면 위치, 관련 책임, 실제 문제, 대안, 변경 비용을 평가한다. 취향만으로 결함을 단정하지 않는다.
5. 필요한 스타일 리팩터링이 별도 의도라면 현재 행동에 섞지 말고 후속 변경으로 제시한다. 사용자가 이미 승인한 범위라면 작은 단위로 계속한다.
6. 예외를 선택했다면 **적용 규칙 → 적용하지 않은 위치 → 이유 → 계약/캡슐화에 미치는 영향**을 짧게 남긴다.

예외 설명 예시:

> getter 금지 기준을 검토했다. 렌더링 경계에서 불변 결과를 전달하는 조회는 유지했다. 반환 객체가 내부 가변 상태를 노출하지 않으며, 도메인 판단은 상태 소유 객체에서 수행한다.

기능 테스트 통과와 스타일 검토 결과는 구분한다. 규칙 수나 통과 개수만으로 설계 품질이 좋아졌다고 주장하지 않는다. 이 스킬만 사용해도 적용할 수 있으며 별도의 작업 흐름 스킬을 요구하지 않는다.
