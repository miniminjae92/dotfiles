# 요구·책임·계약 기반 작업

프로그래밍 미션을 요구사항부터 작고 검증 가능한 행동까지 추적한다. 먼저 사용자가 요청한 방식이 구현, 코드 리뷰, 설명·코칭 중 무엇인지 확인하고 그 범위에 맞춰 행동한다.

## 범위와 근거

- 미션 원문의 필수 요구와 사용자가 명시적으로 선택한 리뷰 대응·설계 결정을 구분해 기록한다. 원문 밖의 개선 제안이나 테스트가 정한 동작을 승인된 요구로 간주하지 않는다.
- 중요한 요구 해석이나 사용자 판단이 필요한 정책이 남아 있으면 선택지와 영향을 설명하고 결정을 기다린다. 합의된 범위 안의 일상적인 구현 선택은 재확인 없이 판단한다. 독립적으로 진행할 수 있는 조사와 작업은 계속한다.
- 기존 코드, 테스트, 요구사항·책임 문서를 함께 읽는다. 문서의 누락이나 모순은 구현에 맞춰 조용히 고치지 말고 근거와 함께 드러낸다.
- 코드 리뷰나 설명·코칭 요청은 검토 결과와 권고를 제공한다. 사용자가 구현이나 수정을 요청하지 않았다면 코드를 변경하지 않는다.

## 구현 흐름

1. 합의한 범위와 요구의 출처를 정리한다. 요구사항은 미션 필수 항목과 승인된 추가 결정에서만 가져온다.
2. 프로젝트의 기존 책임 문서, 특히 `responsibilities.md`가 있으면 읽고 기존 책임과 계약을 보존한다. 다음 행동에 필요한 계약이 있는지 확인하고, 없으면 검증 전 상태인 `[ ]`로 추가한다. 객체의 책임, 공개적으로 관찰되는 계약, 필요한 협력과 실패 전달을 정리한다.
3. 남은 계약 중 의존성이 적고 독립적으로 검증할 수 있는 최소 행동을 다음 작업으로 고른다. 독립 검증은 여러 객체가 필요한 협력 테스트를 배제한다는 뜻이 아니다.
4. 새 동작이나 버그 수정은 최소 구현 전에 계약 테스트를 실행한다. 해당 동작의 assertion이 실패하는지 확인하고, 컴파일·환경 오류나 무관한 기존 실패를 Red로 취급하지 않는다. 이미 동작하는 기능의 테스트 보강이나 동작 보존 리팩터링은 인위적으로 실패를 만들지 말고 기존 동작과 검증 근거를 기록한다.
5. 필요한 최소 코드만 구현하고 관련 테스트를 실행한다. 적절한 회귀 테스트를 확인하고, 전체 검증은 변경 범위와 프로젝트 기준에 맞는 시점에 수행한다.
6. 구현·테스트·문서 diff를 함께 검수한다. 검증된 계약만 `[x]`로 표시하고, 미완료 계약에서 다음 최소 행동을 `[ ]`로 선택한다.
7. 의미 있는 작업 단위가 완료되면 합의된 커밋 정책을 따른다. 커밋은 push나 외부 게시 권한을 뜻하지 않는다.

테스트 이름은 프로젝트 필수 관례를 우선하고 기본적으로 `given_when_then` 형식을 사용한다. 의미 있는 Given 조건이 없으면 Given을 생략할 수 있다. 테스트는 객체의 private 메서드나 단순 getter가 아니라 공개적으로 관찰되는 계약을 검증한다.

책임 문서는 프로젝트의 기존 형식을 따른다. 별도 형식이 없을 때는 다음처럼 객체 책임과 계약을 간결하게 적는다. 체크 상태는 실제 검증 결과에 맞춘다.

```markdown
## HandlerMapping

### 책임

요청에 대응하는 Handler를 반환한다.

### 계약

- [ ] 요청과 일치하는 Handler가 있으면 반환한다.
- [ ] 요청과 일치하는 Handler가 없으면 null을 반환한다.
```

## 책임 문서 보존

- `responsibilities.md`의 기존 책임, 계약, 미완료 상태를 코드 요약을 위해 삭제하거나 축소하지 않는다. 기존 문서는 필요한 줄만 추가·수정하고, 편집 전후 diff에서 삭제와 의미 변경을 확인한다.
- 계약의 의미를 변경·삭제할 때는 근거와 영향을 제시하고 사용자 또는 마스터와 결정한다. 단순한 문구 다듬기는 의미를 보존하면 추가 승인을 요구하지 않는다. 이미 승인된 계약 이관은 이전 위치와 새 위치를 추적하며, 승인받은 결정을 반복해서 묻지 않는다.
- 책임 문서는 구현의 현재 모습을 요약하는 문서가 아니라 보장할 행동과 구현을 평가하는 기준이다. 구현이 계약을 만족하지 못하면 미완료로 남긴다.
- 요구사항 문서에는 미션의 필수 요구와 사용자가 승인한 추가 결정만 기록한다. 구현 결과만으로 요구를 추가·수정하지 않는다. 책임 문서는 승인된 요구·정책과 검증 결과를 대조해 갱신한다.
- 완료 표시는 코드 작성만으로 하지 않는다. 관련 테스트 또는 적절한 실행 근거를 확인한 뒤 표시한다.

## 책임과 구현 세부사항

책임·계약에는 객체가 제공하는 외부 행동과 결과를 적는다. private 메서드, 내부 자료구조(Map 등), Reflection 사용, 내부 register 절차나 실행 순서는 구현 선택으로 둔다. 객체 생성도 일괄 금지하지 않는다. Scanner나 Factory가 인스턴스를 제공하는 일이 목적이면 “지정된 Controller 인스턴스를 제공한다”처럼 외부 책임으로 쓸 수 있고, `new`·reflection·cache 중 어떤 방법을 쓰는지는 적지 않는다.

## 리뷰 흐름

리뷰는 구현 → 테스트 → 계약 → 책임 → 요구 순으로 대조한다. 이 순서는 구현을 기준으로 문서를 고치는 절차가 아니다. 각 변경이 테스트와 계약을 만족하는지, 계약이 책임과 승인된 요구에 근거하는지 확인한다. 불일치는 구현 결함, 문서 누락·모순, 아직 결정되지 않은 정책으로 분류하며 요구사항을 자동으로 구현에 맞추지 않는다. 리뷰 요청만 받은 경우 발견 사항과 권고를 보고하고 수정은 요청 범위에 포함될 때 수행한다.
