# Test List

요구사항에서 다음에 검증할 외부 행동을 고른 뒤, 구현에서 배운 내용으로 목록과 설계 기록을 계속 리팩터링한다. 문서는 테스트 사례를 미리 완성하는 명세서가 아니라 다음 Red를 고르고 중요한 판단을 복원하는 작업대다.

## 근거로 사용할 것

현재 대화, 미션 요구사항, 기존 설계 문서, 테스트, 코드 변경, 실행 결과를 함께 읽는다. 사용자가 확정한 내용과 코드나 테스트로 확인된 사실을 우선한다. 정황상 그럴듯한 판단은 확정하지 말고 `추천안`으로 표시한다.

기존 문서가 있으면 그 구조와 표현을 보존한다. 사용자가 검토만 요청하면 파일을 수정하지 않는다. 문서 작성이나 구현까지 요청했고 작업 문서가 지정되어 있으면 그 문서를 직접 갱신한다.

## 테스트 목록 만들기

1. 핵심 요구사항을 클라이언트나 공개 인터페이스에서 관찰 가능한 행동으로 다시 쓴다.
2. 다른 미완료 행동을 가장 적게 전제하는 행동을 고르고, 요구사항 바로 아래에 다음 수직 조각으로 시작할 체크박스 하나만 둔다. 구현이 쉬워 보이는지가 아니라 선행 관계로 순서를 정한다.
3. 그 행동의 테스트 경계와 더 작은 공개 인터페이스는 `tdd`에서 Red를 작성하며 도출한다. 응답 필드, assertion, 입력 사례를 문서에서 먼저 하위 테스트로 완성하지 않는다.
4. 한 조각이 끝날 때마다 구현에서 드러난 독립 행동만 추가하고, 잘못 나눈 항목은 이름 변경, 이동, 병합, 삭제해 목록을 리팩터링한다.

테스트 항목은 **what**, 즉 어떤 입력이나 상황에서 어떤 행동이 관찰되어야 하는지를 쓴다.

가장 작은 책임은 TDD 과정에서 응집된 모듈과 공개 인터페이스로 도출할 수 있는 하나의 관찰 가능한 행동이다. assertion 하나, 코드 한 줄, 테스트 fixture나 응답 문자열을 자르는 보조 로직을 별도 책임으로 분해하지 않는다. 같은 큰 공개 인터페이스를 assertion별로 반복 검사하는 것도 책임 분리가 아니다.

좋은 항목:

```markdown
- [ ] CSS 리소스 요청에 `text/css`로 응답한다.
- [ ] Query String이 없는 URI에서 경로 전체를 반환한다.
```

구현 방법을 먼저 고정한 항목:

```markdown
- [ ] `ContentType` 열거형을 만든다.
- [ ] `parseQueryString()` 메서드에서 `split`을 호출한다.
```

클래스 생성, 메서드 호출, 알고리즘, 내부 협력 객체가 중심이면 how일 가능성이 높다. 그 구조 자체가 요구된 공개 API인 경우에만 테스트 대상으로 인정한다.

목록에 요구되지 않은 기능이나 추측한 예외를 채워 넣지 않는다. 테스트 하나는 독립적으로 변경될 수 있는 관찰 가능한 행동 하나를 보장한다. `그리고`로 이어진 규칙이나 서로 다른 이유로 실패할 규칙은 분리 후보지만, 실제 분리는 Red와 공개 인터페이스를 설계할 때 결정한다.

사용자가 먼저 초안을 작성했다면 정답 목록으로 교체하지 않는다. 현재 행동의 성공과 실패를 외부에서 무엇으로 관찰할 수 있는지 질문해, 사용자가 빠진 검증 기준을 직접 도출하도록 돕는다. 한 번에 가장 큰 빈틈 하나와 작은 힌트만 제시하되, 상태 코드와 헤더처럼 요구사항을 증명하는 관찰값이 모두 문서에 드러날 때까지 이어간다.

사용자가 전체 초안 작성, 직접 수정, 정답 제시를 요청하면 더 이상 질문 뒤에 답을 숨기지 말고 필요한 항목을 완성한다. 그 경우에도 아직 구현에서 확인되지 않은 사례는 확정하지 말고 후보나 추천안으로 구분한다.

체크박스는 대응하는 테스트가 존재하고 통과할 때만 완료한다. 구현이 존재하거나 더 넓은 테스트가 간접적으로 지나간다는 이유만으로 작은 책임의 테스트를 완료 처리하지 않는다.

## 설계 판단 돕기

다음 순간에 세션 기록을 다시 읽고 설계 기록이 필요한지 판단한다.

- 요구사항을 테스트 목록으로 처음 분해한 직후
- 다음 테스트로 가기 전에 둘 이상의 실제 선택지가 생겼을 때
- 구현 때문에 테스트 목록이나 책임 경계가 의미 있게 바뀌었을 때
- 테스트나 실행 결과가 기존 가설을 반박했을 때
- 한 단계의 완료를 선언하기 직전

모든 코드 선택을 기록하지 않는다. 대안, 제약, 장단점, 이후 변경 비용 중 하나라도 있어 코드만 보고 이유를 복원하기 어려운 판단만 기록한다.

### 사용자가 먼저 작성한 경우

다음 기준으로 냉정하게 검토한다.

- `고민`: 실제로 답이 열려 있던 질문과 그 판단이 필요한 조건이 드러나는가?
- `결정`: 선택한 방향이 한 문장으로 명확하며 현재 코드와 일치하는가?
- `근거`: 요구사항, 제약, 관찰된 증거가 결정을 직접 지지하는가? 실제로 고려한 대안과 감수한 비용이 빠지지 않았는가?
- `검증`: 동작에 관한 결정이라면 테스트나 실행 결과로 유효성을 확인할 수 있는가?

검토 결과는 `빠진 점`, `표현 제안`, `추천 수정안`으로 제시한다. 중요한 누락이 없으면 억지로 항목을 만들지 말고 그대로 충분하다고 말한다. 문장을 대신 화려하게 쓰기보다 모호한 주장, 사후 합리화, 근거와 결론의 비약을 고친다.

### 아직 작성하지 않은 경우

세션에 실제 설계 판단이 있으면 아래 형식으로 초안을 제시한다. 사용자가 명시적으로 선택하지 않은 `결정`은 `추천안`으로 표시하고 확정 기록으로 승격하지 않는다.

```markdown
### [쟁점]

#### 고민

[무엇이 불확실하며 어떤 조건 때문에 선택이 필요한가]

#### 결정

[선택한 방향 한 문장]

#### 근거

[결정적인 요구사항이나 증거, 비교한 대안, 감수한 비용]

#### 검증

[결정을 확인할 테스트나 실행 결과]
```

`검증`은 동작 가설이 있는 결정에 사용한다. 아직 검증 전이면 결과를 꾸며내지 말고 검증할 관찰값을 적는다.

## 문서 형태

기존 문서의 제목과 구조를 보존한다. 별도의 `테스트 목록` 제목을 강제하지 않고 각 요구사항 바로 아래에 체크박스를 둔다. 새 문서가 필요할 때는 다음 최소 구조를 사용한다.

```markdown
# [미션 또는 단계]

## 핵심 요구사항

### [요구사항]

- [ ] [다음에 검증할 외부 행동]

## 설계 기록

### [쟁점]

#### 고민

#### 결정

#### 근거

#### 검증
```

단계가 끝나면 미완료 테스트, 요구사항 전체를 증명하는 테스트, 현재 코드와 어긋난 결정이 없는지 감사한다. 완료된 세부 테스트의 정본은 테스트 코드다. 문서에는 요구사항의 구조와 복원 가치가 있는 판단을 남기고, 테스트 코드를 그대로 나열한 중복은 압축한다.

실제 테스트 설계나 제품 코드 구현으로 넘어가면 `tdd` 스킬을 함께 적용한다. 이 목록은 다음 Red의 후보를 고를 뿐, 테스트 사례, 공개 인터페이스, assertion을 미리 확정하지 않는다.
