# Testing

**서비스가 보장해야 할 계약을 발견하고, 적절한 경계에서 효율적으로 검증한다.** 여기서 계약은 시스템이 보장하기로 한 관찰 가능한 동작이다.

서비스가 커져도 에이전트와 사람이 합의된 계약과 검증 위치를 찾아볼 수 있도록 `TESTMAP`를 유지한다. 흩어진 대화나 일부 코드만으로 계약을 추측하는 일을 줄이는 것이 목적이다.

## 핵심 원칙

### 1. 계약을 먼저 본다

테스트를 작성하기 전에 무엇을 보장해야 하는지 파악한다.

- 요구사항, 공개 인터페이스, 기존 동작, 버그, 설계 결정에서 계약의 근거를 찾는다.
- 정상 동작뿐 아니라 실패/예외, 경계값, 불변식, 상태 전이, 외부 시스템 경계, 도메인 특유의 위험을 검토한다.
- 근거가 불명확한 동작은 확정된 계약으로 만들지 말고 **계약 후보**로 제안한다.
- 새로운 정책이나 기존 계약의 의미 변경이 필요한 후보는 이유와 영향을 설명하고 사용자의 판단을 받는다.
- 이미 명시적으로 합의된 요구사항은 다시 승인받지 말고 계약으로 사용한다.

### 2. TESTMAP를 유지한다

`TESTMAP`는 이 스킬에서 사용하는 고유 문서명이며, 서비스의 계약과 그 검증 근거를 모은다. 기본 위치는 프로젝트 루트의 `TESTMAP.md`다. 프로젝트에서 이미 같은 역할을 하는 문서나 별도 위치를 정했으면 그 문서를 재사용한다.

테스트나 제품 코드를 추가하거나 변경하는 작업에서는 해당 계약을 기록하거나 갱신한다. 문서가 없으면 기본 위치에 만든다. 계획이나 리뷰만 요청받았으면 계약과 수정 제안을 반환한다.

TESTMAP에는 다음을 남긴다.

- 보장할 계약
- 계약의 근거
- 계약을 책임지는 경계
- 검증 방법 또는 테스트 수준
- 상태와 검증 근거

계약을 읽거나 기록할 때 형식과 상태 규칙은 [TESTMAP 작성 규칙](references/testmap.md)을 따른다. 먼저 기능별 제목이나 검색으로 관련 계약을 찾고, 그 계약의 근거와 검증 위치를 읽는다. 기록과 실제 요구사항, 코드 또는 실행 근거가 어긋나면 그 차이를 확인하고 갱신한다.

### 3. 계약을 책임지는 경계에서 검증한다

각 계약은 그 계약을 실제로 책임지는 경계에서 검증한다.

- 도메인 규칙은 도메인/단위 경계에서 검증한다.
- DB 매핑, 제약과 트랜잭션은 실제 저장소 경계에서 검증한다.
- HTTP 상태, 헤더와 본문 같은 API 계약은 API 경계에서 검증한다.
- 전체 시스템 연결과 핵심 사용자 흐름은 E2E에서 검증한다.

계층 이름에 맞춰 테스트를 억지로 만들지 말고 **그 계층에서만 확인할 수 있는 계약이 있는지** 먼저 판단한다.

실제 기술 경계 통과가 계약의 일부라면 그 경계를 통과해 검증한다. mock으로 통과를 대신하지 않는다.

### 4. 필요한 신뢰도를 만족하는 가장 낮은 비용의 검증을 선택한다

같은 계약을 여러 방식으로 검증할 수 있다면 필요한 신뢰도를 유지하면서 비용이 가장 낮은 방법을 선택한다.

비용에는 다음을 포함한다.

- 실행 시간
- 환경과 데이터 준비
- 유지보수 비용
- 실패 원인 진단 비용
- 외부 시스템 의존성

상위 계층 테스트는 하위 계층으로 증명할 수 없는 경계나 연결을 검증할 때 추가한다.

### 5. 계약 중복을 검사한다

새 테스트를 추가하거나 기존 테스트를 정리할 때 TESTMAP의 관련 계약과 연결된 테스트를 먼저 확인한다. 연결이 누락되었거나 중복 여부가 불분명하면 저장소 검색으로 범위를 넓힌다.

- 같은 입력, 행동과 관찰 결과를 의미 없이 반복하지 않는다.
- 비슷한 시나리오가 여러 계층에 있어도 각 테스트가 서로 다른 경계의 계약을 증명한다면 유지할 수 있다.
- 새로운 보장을 추가하지 않는 반복 테스트는 중복 후보로 본다.
- 중복 후보를 발견하면 무엇이 겹치는지, 각 테스트가 실제로 보장하는 것이 무엇인지, 제거하거나 통합할 때 잃는 신뢰도가 있는지를 사용자에게 설명한다.
- 의미 있는 테스트 삭제나 계약 변경은 사용자 판단 없이 수행하지 않는다.

### 6. 테스트를 실행 가능한 명세로 작성한다

**테스트 실행 결과만 보고도 기능의 요구사항과 시나리오 구조를 파악할 수 있어야 한다.**

- 관련 테스트를 기능과 상황별로 계층화한다.
- 테스트와 그룹 이름을 사람이 읽을 수 있는 요구사항 문장으로 작성한다.
- 현재 언어와 테스트 프레임워크가 제공하는 관용적인 명세 기능을 적극 사용한다.
- 예: JUnit은 `@Nested`, `@DisplayName`, Jest는 `describe`/`it`, RSpec은 `describe`/`context`/`it`를 활용한다.
- 의미를 추가하지 않는 계층은 만들지 않는다.

### 7. 구현이 아니라 관찰 가능한 계약을 검증한다

- 공개 경계를 통해 결과를 관찰한다.
- 테스트 하나는 독립적으로 바뀔 수 있는 관찰 가능한 동작 하나를 책임진다.
- private 메서드, 내부 자료구조, 내부 호출 순서처럼 외부 계약이 아닌 구현 세부사항을 직접 고정하지 않는다.
- 리팩터링만 했는데 관련 계약이 그대로인데도 테스트가 깨진다면 구현 결합을 의심한다.
- 내부 협력 호출 자체가 계약인 경우가 아니라면 mock 호출 횟수나 순서를 결과보다 우선하지 않는다.
- 기대값을 프로덕션 코드와 동일한 알고리즘으로 다시 계산하는 동어 반복 테스트를 피한다.

## 작업 흐름

테스트 관련 작업을 다음 순서로 판단한다. 필요 없는 단계는 생략하되 순서를 뒤집어 구현에 맞춰 계약을 만들지 않는다.

1. TESTMAP에서 관련 계약을 찾고, 연결된 요구사항과 기존 테스트, 코드를 읽는다. 아직 문서가 없으면 관련 요구사항과 코드에서 시작한다.
2. 현재 보장되는 계약과 새로 필요해 보이는 계약 후보를 구분한다.
3. 계약 후보가 제품 정책이나 동작을 추가하거나 변경한다면 사용자에게 간결하게 제안한다.
4. 각 승인된 계약의 책임 경계와 현재 검증 여부를 확인한다.
5. 필요한 신뢰도를 만족하는 가장 낮은 비용의 테스트 수준을 선택한다.
6. 기존 테스트와 계약 중복을 확인한다.
7. 테스트를 실행 가능한 명세 형태로 작성하거나 정리한다.
8. 관련 테스트를 실행하고 실제로 검증한 계약만 TESTMAP에 실행 근거와 함께 `verified`로 반영한다. 필요한 회귀 검증 범위는 변경 영향에 따라 정한다.

## 계약 후보를 제안할 때

사용자가 판단할 수 있도록 한 후보마다 다음만 간결하게 설명한다.

- **계약 후보**: 무엇을 보장할 것인가
- **발견 이유**: 정상/예외/경계/불변식/도메인 위험 중 왜 검토하는가
- **영향**: 채택하면 시스템이 무엇을 보장해야 하는가
- **검증 비용**: 어느 경계에서 어떤 테스트가 필요한가
- **추천**: 채택/보류 중 추천과 이유

후보를 조용히 테스트로 확정하지 않는다.

## 리뷰할 때

개별 테스트보다 먼저 계약과 검증 구조를 본다.

1. 이 테스트가 어떤 계약을 증명하는가?
2. 그 계약의 책임 경계에서 검증하고 있는가?
3. 더 낮은 비용으로 같은 신뢰도를 얻을 수 있는가?
4. 저장소의 다른 테스트와 같은 계약을 반복하지 않는가?
5. 테스트 실행 결과가 요구사항 문장과 시나리오 구조로 읽히는가?
6. 구현만 바뀌어도 깨지는 테스트는 아닌가?

## 작업 유형별 적용

- **새 기능**: 계약과 후보를 먼저 파악한 뒤 적절한 경계에서 검증한다.
- **버그 수정**: 수정 전 코드에서 회귀 테스트가 해당 버그 때문에 실패하는지 확인하고, 수정 뒤 같은 테스트의 통과를 확인한다. 빌드 오류나 환경 오류는 버그 재현으로 보지 않는다. 재현 환경을 확보하지 못하면 그 한계를 보고한다.
- **리팩터링**: 기존 계약과 검증 근거를 확인하고 동작 보존을 검증한다. 실패를 인위적으로 만들지 않는다.
- **기존 테스트 정리**: TESTMAP에서 연결된 테스트를 확인하고 필요한 저장소 검색을 통해 중복, 잘못된 경계, 구현 결합을 우선 찾는다.
- **계획과 목록**: 미검증 계약에서 다음에 확인할 동작을 고른다. 목록만 요청받았으면 관찰 가능한 동작의 목록을 반환한다. 별도 테스트 목록 문서는 강제하지 않는다.
- **TDD**: 사용자가 TDD를 요청하거나 프로젝트가 요구할 때만 Red → Green을 적용한다. 관찰 가능한 동작 하나의 의도한 실패를 확인하고, 통과에 필요한 만큼 구현한 뒤 다음 동작으로 진행한다. 이미 구현된 동작의 테스트 보강이나 특성화 테스트를 TDD라고 부르지 않는다.
