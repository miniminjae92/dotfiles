# TESTMAP 작성 규칙

TESTMAP는 서비스가 보장하기로 한 계약과 그 근거, 책임 경계, 검증 위치와 상태를 모은 문서다. 서비스가 커지고 작업 대화가 바뀌어도 에이전트와 사람이 같은 보장을 찾아 확인하는 진입점으로 사용한다.

기본 위치는 프로젝트 루트의 `TESTMAP.md`다. 이미 같은 역할을 하는 프로젝트 문서가 있으면 그 문서를 재사용한다. 요구사항과 설계 결정의 출처를 연결하고, 각 계약을 관찰 가능한 동작으로 요약한다.

## 기본 형식

기능이나 도메인 단위로 묶고 다음 표를 사용한다.

```markdown
# TESTMAP

## 회원가입

| 계약 | 근거 | 책임 경계 | 검증 | 상태 | 근거/테스트 |
| --- | --- | --- | --- | --- | --- |
| 중복 이메일로 가입할 수 없다 | 요구사항의 회원가입 항목 | 회원가입 도메인 | Unit | approved | 아직 미검증 |
| 이메일 유일성은 저장소에서도 보장된다 | 설계 결정 | Persistence | Integration | approved | - |
| 이메일 대소문자를 동일하게 취급한다 | 도메인 정책 후보 | 회원가입 도메인 | 미정 | candidate | - |
```

## 상태

- `candidate`: 검토가 필요하지만 아직 계약으로 확정하지 않은 항목
- `approved`: 사용자가 승인했거나 명시된 요구사항으로 확정된 계약
- `verified`: 적절한 테스트나 실행 근거로 실제 검증된 계약

`approved` 계약에서 확인 근거를 확보했을 때 `verified`로 올린다. `candidate`는 테스트가 통과해도 사용자 판단이나 명시된 요구사항 없이 확정된 계약으로 승격하지 않는다.

## 관리 규칙

- 명시된 요구사항은 바로 `approved`로 기록할 수 있다.
- 제품 동작이나 정책을 새로 만드는 항목은 `candidate`로 제안하고 사용자 판단을 받는다.
- 테스트가 존재한다는 이유만으로 요구사항을 새로 만들지 않는다.
- `verified`에는 실행 명령이나 관찰 방법, 결과, 확인 시점과 검증한 코드/환경을 남긴다. 테스트의 존재만으로 검증 완료를 표시하지 않는다.
- 관련 계약이나 코드/환경이 바뀌어 기존 근거가 더 이상 적용되지 않거나 재검증이 실패하면 `approved`로 되돌리고 현재 한계를 남긴다.
- 기록할 때 해당 작업에서 실제로 확인한 범위를 표시한다. 일부 테스트 통과를 서비스 전체의 검증 완료로 확대하지 않는다.
- 같은 계약을 여러 테스트가 검증한다면 테스트를 모두 나열하기보다 각 테스트가 서로 다른 경계를 증명하는지 먼저 판단한다.
- 기능별 제목이나 검색으로 관련 계약을 찾고, 연결된 근거와 테스트부터 읽는다. 연결이 빠졌거나 기록과 실제 동작이 어긋나면 필요한 코드와 테스트까지 확인해 갱신한다.
- 기록이 없다는 이유만으로 계약이 없다고 판단하지 않는다. 새로 발견한 동작은 근거를 확인해 기존 계약 또는 후보로 구분한다.
